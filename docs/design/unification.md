# Design: moving every language onto the shared core

Goal: a `lang-*` crate holds only facts of its language: its grammar, its tool's quirks as data, and the rare rule that no other language could ever state. Everything that can be generic is generic, even with one consumer today: JS/TS, Python, HTML and its dialects, CSS/SCSS/Less, SQL, C#, YAML, Markdown, Java, shell and the rest stop carrying their own copies of what the shared core has or should have, and rules that check the same thing share one id and one implementation. The method of [shared-core.md](shared-core.md) holds: roles from the grammar, kits in `core-format`, one binder and one flow builder, pattern rules and families with data rows, policy in `lang.yaml`. This note is the plan, not the work. It is deleted when its last step lands; each step updates the docs of the area it changes.

"This language is older than the kit", "it has its own family", "no second consumer yet" and "the reference tool's algorithm is special" are not reasons to keep code in a language crate. A tool's quirk is a named option or a data row; the algorithm is written once. Section 5 lists the mechanisms found by a sweep of every `lang-*` crate, `scripts/` and `xtask`, with the copies, the core home and what stays as data.

## 1. Where the lines are (main at `f9f98ec3`)
`scripts/cost.sh --languages`: shared crates 30,971 lines, `lang-*` 78,742, shared share 28.2%. Formatter 33.0k, rules 23.2k.

- **Ids are already mostly one per thing.** 722 rule ids, 647 released in 0.0.2. 94 ids cover `css`+`less`+`scss` and 128 cover the four HTML dialects (one crate, one id). Cross-language ids exist today: `no-self-compare`, `no-constant-condition`, `no-constant-comparison`, `no-assignment-in-condition`, `no-empty-block` (shared pattern files, K1), `no-duplicate-case`, `no-duplicate-keys`, `no-empty-keys`, `key-name-casing`, `sorted-*`, `max-line-length`, `comment-space`, `no-empty-comment` (shared Rust), `unused-import`, `unused-local-variable`, `naming-convention`, `unused-variable`, and the YAML set shared with GitHub Actions. What is left to merge is 36 ids that name the same finding in several languages (section 3), plus code that is the same under different ids.
- **Many rule lines are real per-language knowledge, many are not.** About 200 Rust checks average 30 lines each (Python `control.rs`: `try_except_pass` 23, `blind_except` 31; Ruby `clauses.rs`: `rescue_exception` 13, `suppressed_exception` 26; JS `misc.rs`: `self_assign` 15). Moving a check to a role rule saves its 15-50 lines, not a file. The large blocks are: the scope rules of JS and Python (about 3,100 lines with their tables), CSS's name families (794), Python's ruff families that exist in no other language (`isort` 712, `%`-format 579, pyupgrade 417), C# documentation rules (about 1,950), JS regex rules (307).
- **Formatters are the bigger target.** Python uses no shape of `core_format::shapes`; JS keeps call arguments, objects, parameters, statements, `needs_parens` and TS types (about 4,400 of its 7,959 lines) as its own code; C# keeps lists, braces and sequences (1,425 of 3,327); CSS, YAML, Markdown, HTML, SQL and shell are on the document printer but on no shape.
- **The sweep (section 5) finds the same again outside rules and layout.** Token spacing is written four times (Java `space.rs` 75, Kotlin 173, C# `spacing.rs` 106, SQL 252), the node-sequence helpers three times (C# `seq.rs`, Kotlin and Java `format/mod.rs`: `kids`, `first`, `last`, `el`, `kw`, `break_after`, `multiline`, `between`), source rewrites twice (JS `rewrite.rs` 481, Kotlin 333), import ordering four times (Python 712, C# 685, Java 87, Kotlin about 45), comment tracking twice beside `core_format::comments`, the hand-written parsers' cursor, trivia and error plumbing six times (JSON, CSS, Java, SQL, C/C++, YAML), the string-literal model in about twelve places, and the scope tables of six languages as Rust. The last 30 commits added `lang-python` +3.7k, `lang-sql` +5.0k, `lang-ruby` +1.5k, `lang-html` +1.6k, `lang-kotlin` and `lang-php`: almost all of it is a mechanism with a generic home (SQL's parser and layout, Python's rule checks and `isort`, Ruby's checks, the Vue script reader, Kotlin's rewrite and spacing, PHP and Kotlin scope tables).

Estimate for the whole plan (lines of hand-written Rust, from the measured files, the shared lines the plan adds counted; data rows in `lang.yaml`, grammar tags and data files are not Rust and are named per group): formatter steps about -12,500 in `lang-*` and +4,700 shared; rules, scopes, parsers and other mechanisms about -13,500 and +7,100. Net about -14,200 lines: `lang-*` from 78.7k to about 52.7k, shared crates from 31.0k to about 42.8k, the shared share from 28.2% to about 45%. Every number is an estimate to be replaced by the step's own `scripts/cost.sh` output; a step that misses its estimate by half stops and reports.

## 3. Clusters
A cluster is rules that check the same thing. Two kinds: **A. one id** (the ids are merged, the new id has a row per language) and **B. one implementation, ids stay** (the tool-specific ids are kept as rows of a shared family, because their options, defaults or reference-tool ids differ and nothing would be gained by merging). Lines are the estimate of section 1: `lang` removed from `lang-*`, `shared` added. Catalog equivalents are the `docs/parity/*.yaml` entries whose `rule <id>` changes.

## 4. Rule ids change
The API is unstable (user decision): renamed and merged ids simply change. No compatibility handling: no aliases, no deprecation warnings, no accepting the old id. The changelog lists every renamed id (36 old ids replaced by 18 new ones; 22 were in 0.0.2). In the same step as each merge: rename the rule file, fixture folder and catalog entries, update presets, `sudsy init --from` mappings (`crates/cli/src/init/`, which debug builds check against the catalog), docs and the generated tables. `cargo xtask rename-rule <old> <new>` does the mechanical part ([../development/testing.md](../development/testing.md#renaming-a-rule)); the init mappings, which spell upstream ids, and the changelog are by hand. A shared option that replaces a language option is renamed the same way, presets rewritten in the same step (presets stay pure data). A catalog entry may name several ids (`no-unused-vars: rule unused-variable, unused-parameter, unused-import`); `sudsy rules` lists the entry under each id; the ESLint `init` mapper applies the level to each, the other mappers read one id and are extended by the step that adds an entry they meet. `scripts/parity_lint.py` folds the later ids of such an entry into the first before comparing (fixtures and coverage; L2, `no-unused-vars`).

Decisions (lead and user): formatter steps get no ratchet allowance (the ratchet rule of section 5 holds as written); the unused cluster is three ids, `unused-variable`, `unused-parameter`, `unused-import`, the old `no-unused-vars` gone; empty catch bodies move from `no-empty-block` to `no-empty-catch`, the same findings under another id.

Rules (user): a mechanism needed by a second language is built in the shared core in that step, never copied; a language being older than the kit is never a reason it stays off it. A language crate holds only facts of that language (grammar, tags, data tables, `lang.yaml` values); every mechanism lives in a shared crate even with one consumer, and a missing shared capability is built there in the same step or the gap stays open. CI checks it (`Language-only:` trailer, CLAUDE.md).

## 5. Mechanisms in language crates
Method: every module of every `lang-*` crate, `scripts/` and `xtask` was read for what it does (not what it is called) and compared with `core-*` and with the other languages. A mechanism that two languages implement, or that one language implements and another could use, has a core home; the language keeps the facts. Line counts are of the main commit; "data" is what the language still states (`lang.yaml` rows, grammar tags, `.txt` or `.yaml` data files, presets).

### Formatter rules
Rules from [shared-core.md](shared-core.md) hold: a ratchet (`tests/parity/*/differences.yaml`: files identical, second-format, refused) may only improve during a step; decision 1's 2-point allowance was for the pilot and is **not** assumed here (the lead may grant it per step). Presets and policy: a difference between tools is a named option in `lang.yaml` (declared once in `core_config::shared` when two languages have it), never a branch on a language or preset. Bench: a language's format up to +5%, every other language and metric +1% (CLAUDE.md); L1-L2 showed role-driven layout costs 2-6% where `Grammar::slot` is read, so JS and Java steps carry that risk.

## 6. Steps
Rule for every step: a mechanism that can be generic is built in the shared core in that step, whether one language or five use it, and the language keeps only data; that a language is older than the kit, has its own family, or that its tool's algorithm is special is never a reason it stays. Review of a step: `scripts/cost.sh --languages` before and after, in the commit message; every ratchet holds; the docs of the area are updated. Bench budget of a step while this plan is open: every metric up to +3% (CLAUDE.md); rules turned on by default keep their +40% lint budget, and `bench/budgets.txt` caps still apply.

One step is one commit and one finish run, in one area. Order: what unblocks the others first, then lines per effort. Three tracks run in parallel: formatter (F), rules and scopes (L, W), parsers and infrastructure (A, P, E, C, X). Steps with `After` empty can start now.

Landed with the PHP formatter (the first language that is only data): `core_format::spacing` (token spacing rows: `[space]`, `[joined]`, `[at_least_one]`, `[op_first]`), `core_format::rewrite` (token rewrite rows: replace, insert), `core_format::layout` (node layout rows: `document`, `scope`, `braced`, `with_body`, `block`, `case`, `colon_body`, `list`, `array`, `braced_list`, `heritage`, `chain`, `cases`, `verbatim`) and `core_format::rules` (`LazyRules`: one rules file per language, parsed on first use, is the language's `NodeFormatter`), on `shapes::flow::Flow` (token-sequence layout; Kotlin's `seq` is on it too). `crates/lang-php/format.rules` is the whole PHP formatter. F2 ports Java, Kotlin, C# and the other token-spacing code onto the spacing rows (their tables become rows; rows may need new conditions in `Pattern`), W1 ports the rewrites onto the rewrite rows (new actions as needed: moving and splitting statements, which PHP's dropped trait-`use` split needs), F7 ports declaration layouts onto the `layout` shapes.

Running elsewhere now (this plan folds them in, does not redo them): **L1** (rename tooling, slot 5), **F1** (`core_format::literals` on JS, Python, CSS, YAML, slot 1), **Kotlin formatter step 2** (slot 2), **PHP formatter** (slot 3), **coverage by preset** (M4, slot 4). Instructions to the running ones: Kotlin step 2 and PHP write no new spacing, sequence helpers, rewrite code or import sort in their crates: spacing is a data row list in the grammar, a rewrite is a rule with a fix, an import order is an option of `sorted-imports`; where the kit does not have it yet, it stays a named gap in their notes (F2, W1, L8 land it and port them).

## 7. What stays in a language crate
Only facts of the language, in this form:
- its grammar and role tags, spacing, case, ignore, trivia and string rows, `scope:` and `embedded:` rows, `limits:` (data, not Rust);
- its parser adapter: the replay of a foreign AST into kinds (Roslyn worker, oxc, ruff, mago, Prism, tree-sitter node maps), and the hand-written parser's grammar productions (JSON, CSS, YAML, HTML, SQL, Java) on `core_syntax::parse`;
- its tool's quirks as options or rows in `lang.yaml`, presets and tables: ruff's isort sections, Prettier's call patterns, sqlfluff's rule values, ktlint's wrap thresholds;
- the rules whose finding is a rule of that language and cannot be stated on roles: Python's `__future__` and mutable-default checks, Roslyn bindings and the worker symbol checks (`symbol_checks.rs`, `finding.rs`), RuboCop's `Lint` classes about Ruby's calls and access modifiers, Vue's `defineProps` reading (`script/props.rs` 604, `keys.rs` 278), the HTML content models and ARIA, CSS property and value knowledge, Dockerfile and shell command semantics, TypeScript-only rules;
- formatter code for a construct no other language has: JSX whitespace, Angular microsyntax and pipes, LINQ `query.rs`, shfmt's arithmetic and `case`, Markdown's block structure, YAML block-scalar folding.

## 8. Decisions needed
1. The SQL formatter (F12) moves from its own token-model engine to the document printer; the bench budget of a format rewrite is +5% for SQL, and the sqlfluff ratchet may not fall. If it cannot hold both, F12 stops with the numbers.
2. The rewrite layer (W1) makes `lint --fix` and the formatter share fixes: a rule marked `format: true` is no longer optional in a preset that reproduces a formatter. Alternative: the formatter keeps its own list of rewrites (a copy per language: rejected by the hard rule).

# Adding a language with tree-sitter

A language whose tree-sitter grammar exists and is good enough costs a grammar file, a small formatter and a `lang.yaml` with a node-name table (the table, the provider glue and `Cargo.toml` are generated from it); `core-treesitter` gives the parser, error recovery and lossless tree. `lang-toml` is the worked example (`lang-xml` adds a layout of its own and well-formedness checks): a grammar of 50 lines and a `lang.yaml` of 50, against about 880 for the hand-written JSON parser and formatter. Hand-written parsers stay the choice where speed, error messages or recovery matter (C#, JSON, YAML, HTML and its dialects); one can replace a tree-sitter parser later without touching anything outside the language crate, because the core sees only our tree. A parser that is a Rust crate with its own AST and tokens (`lang-js`: oxc, `lang-python`: ruff) gets the same generated provider from a `parse: adapter::parse_file` key in `lang.yaml` (`parse_file(&SourceFile) -> ParseResult`; `extensions`, `formatter`, `hooks`, `rules` and `families` as below; its `Cargo.toml` stays by hand) and an adapter to our tree, see below; a hand-written parser with no dialects (`lang-yaml`) uses the same key. A language whose providers differ by dialect builds `ParserProvider::new(ParserSpec { .. }, parse)` by hand in `lib.rs`: `.with_matchers(..)` for matchers that select a dialect or a directory (`lang-json`: JSON and JSONC), `.with_dialect(name, base)` for a dialect with its own provider and config section on a base's (`lang-css`: SCSS and Less on CSS; `lang-html`: Vue and Svelte on HTML, Angular on the same tree through oxc-htmlish-parser and `adapter::replay`; the matcher `*.component.html` is a file-name suffix).

## What an adapter to an external parser does (`provider_api::adapter`)
An upstream library is used for parsing only: layout and fixes are Sudsy's own code on its own tree (a library's formatter or fixer adds its whole rule set and dialects to the binary and cannot be changed by us).
The parser gives tokens (every token of the file, with its span) and an AST. The adapter walks the AST once to collect node spans in pre-order and our kind for each (`KindNames`: the parser's kind name looked up in the grammar on first use, so a node kind is a row in `grammars/<lang>.grammar` named like the parser's kind), maps the tokens to our token kinds, and calls `replay_grammar(src, grammar, tokens, nodes, retag)` (`replay` with explicit `Kinds` and a `scan` function is for hand-written parsers), which builds the tree: a node opens before the first token that starts in it and closes after its last, the text between two tokens is split into whitespace, newlines and what `scan` recognizes (the grammar's `trivia` rows: comments, line continuations), attached by the shared rule, and text that is none of these is an `Unknown` token with a parse error. A parser that recurses runs under `guarded` (the `limits:` map of `lang.yaml`, generated as `LIMITS`: thread stack, file size, nesting; a panic is a refusal) and one that wants `\n` is given `Lf` (offsets map back); `KindNames` looks the parser's kind names up in the grammar (`core_syntax::codegen::from_screaming` turns `VALUE_PARAMETER_LIST` into `ValueParameterList`). `retag` changes a token's kind from the innermost open node (JS: `|` in a union type). `ParseError::syntax` makes the parser's diagnostics. Parser crates (dependencies of `lang-*` crates named `oxc*`, `ruff*`, `ktrs*`, `mago*`, `tree-sitter*`) are named only in `adapter.rs`, an `adapter/` folder or a generated file; `cargo xtask codegen --check` fails on any other file that names one, unless `xtask/parser-imports.txt` lists it (the existing offenders: `lang-js` 5 files, `lang-python` 9, `lang-html` 3, `lang-markdown` 1), and fails on a listed file that no longer does, so the list only shrinks. The adapter files are what is left: kind tables, parenthesis nodes (Python), JSX whitespace (JS), the leaves-as-trivia lookup (SQL).
Test helpers: `format_testing::assert_parses` (round trip, attachment, no errors, no `#error` token, fixed token text), `assert_lossless` (the same for a file with errors), `bench_input_files`, `check_corpus`.

## What the adapter does (`core-treesitter`)
`Engine::new(language, grammar, mapping)` parses with a linked-in tree-sitter `Language` (native C, no Wasm: the Wasm host would link a second wasmtime) and converts the result:
- Every tree-sitter node named in `Mapping::kinds` becomes the kind of our grammar it maps to: a node kind becomes a node, a token kind a leaf (its tree-sitter children are swallowed, so a string with escape sequences is one token; an `ERROR` inside it is reported only if the mapping lists the token in `checked`), a trivia kind (comments) trivia. An unmapped node with children is transparent; an unmapped leaf is an `Unknown` error token. A `from` is the node's name; when a grammar has a rule and a keyword of the same name (protobuf's `message`), write the keyword's entry quoted as in tree-sitter queries (`"\"message\""` matches only the anonymous node, `message` only the named one; with no quoted entry the name matches both).
- Tree-sitter's tree has no whitespace or newlines: the bytes between tokens are rebuilt as `Whitespace` and `Newline` tokens and attached by `provider_api::adapter::Attach`, the loop the external-parser adapters' `replay` runs too (a token takes the trivia before it and after it up to the end of its line), so the tree prints back to the input byte for byte. Text that is neither is an `Unknown` token.
- `ERROR` nodes become `SyntaxKind::ERROR` and a parse error, `MISSING` nodes a parse error. Messages are "syntax error" and "missing X", with no codes or hints.
- `Mapping::wrap`: tree-sitter hides one-part keys and literals as bare tokens, while shapes (`#delimited-list`, `#key-value`) want nodes as items. A token listed there is wrapped in a node of its own, unless its tree-sitter parent already maps to that node.
- A zero-width `Eof` token ends the root; it owns the comments at the end of the file.

## Parser comparison (before step 1)
Which language is next comes from the new-language rows of [../parity/queue.md](../parity/queue.md) (data: `xtask/full/languages.yaml`; a row with estimates is picked only to measure it, and a measured language replaces its estimates there). The first step of a language measures the candidate parsers and stops with a recommendation (CLAUDE.md); the user decides. One table, one column per candidate, on one named machine (CPU, cores, rustc, release with LTO): whole files parsed from memory, warm, best of 5, no adapter, on a pinned corpus of real files (commit SHAs) plus hand-written probes of the newest syntax. Rows, all measured unless marked:

| Row | What it says |
|---|---|
| Kind | Rust or C; hand-written or generated; typed AST or untyped tree; where trivia lives |
| Corpus files with a parse error | count over the whole corpus (the error-free files are the valid set when no reference compiler is installed) |
| Probes failing | newest-version syntax and known awkward constructs (keywords as names, heredocs, alternative syntax) |
| Parse speed | MB/s per corpus |
| Stripped binary added | MB over an empty `main` |
| Tokens with trivia tile the source | yes or no, on every corpus file: whitespace and comments come as tokens and the spans leave no gap or overlap (an adapter needs this; if no, it must rebuild trivia) |
| Mutants: damage by one deleted bracket | share of the file lost to the error (median / p75 / p90) on files with one `)`, `}` or `{` removed |
| Deep nesting | graceful error or stack overflow, and from what depth |
| Dependencies | crate count and build time, and what they pull in |
| Upstream | licence, releases per year, contributors, toolchain (`rust-version` against ours) |
| Maintainers and funding | who maintains it (one person, a team, a company), whether the work is paid or sponsored, how releases and fixes went in the past year |

Name what was not measured ("adapter itself", "memory"). The note ends with the recommendation, its exact pin and the costs accepted; it is deleted when the language's step 1 lands, the decision going into the language's formatting doc. Example: the PHP comparison, `git show e93070f:docs/ai/design/php.md`.

## First deliverable of a language step: the mapping table
A leg with no reference tool is planned by [../development/no-reference-tool.md](../development/no-reference-tool.md): its decision table and checklist take the place of the tool's rows here.

Before code, write a table (in the step's notes) with one row per reference-tool rule or style option and its entry in [../kit/index.md](../kit/index.md) (generated, one row per concept; search it by tool name and by behavior words):
- **index entry** `<id>`: the behavior exists; the language reads its data or uses its module.
- **adopt** `<id>`: the entry is SINGLE-USE or LOCAL (`docs/ai/design/single-use.txt`). The step moves both languages onto the shared form and proves the first language byte-identical (corpus before/after), so the entry leaves the list.
- **deferred** `<row>`: the behavior's shared form is a deferred row of [../design/unification.md](../design/unification.md) (F9 JS layout, F10 CSS layout, P7b parser checkpoint and token-generic lexer). That row runs as its own step first, so the new language uses the shared form and is never the second copy.
- **new** `<id>`: nothing matches. Name the search terms used (index words, `grep` of the tool's rule name over `crates/`). The module declares `//! concept: new <id>` with `what:` and `tools:`; the entry then sits in the single-use list unless a second language adopts it in the same step. A shared module that reads no data (`reads:` only `option:`, `rule:`, `path:`) declares a plain concept instead; codegen adds it to the list as `(shared)` and it leaves when a second language adopts it.

Every module of a shared or `lang-*` crate starts with `//! concept: <id>[, <id>...]` (a language module may also say `none (<reason>)`); shared modules add `what:`, `tools:` and `reads:` (data the mechanism reads: `rules:<section>[.<key>]`, `grammar:<line>`, `tag:<name>`, `option:<name>`, `rule:<id>`, `family:<name>`, `path:<rust path>`). `cargo xtask codegen` writes the index and shrinks the single-use list; `cargo xtask codegen --check` (gate and CI) fails on a missing header, a stale index, an unknown concept id, a new single-use or LOCAL entry, an invalid or shadowed `format.rules` row. `cargo xtask dupes --check` fails on a new or grown duplicate between crates (`docs/ai/design/dupes-baseline.txt`; `cargo xtask dupes --baseline` shrinks it). `land.sh` reviews each growing language crate against the kit index (`scripts/review-hard-rule.md`).

## Steps
1. **Grammar file** `grammars/<lang>.grammar` (format: [syntax-tree.md](syntax-tree.md)). Take a free language id (`language <name> <id> "<Display name>"`, 1 to 31; codegen refuses a duplicate). Declare the trivia tokens (`Whitespace`, `Newline`, the comment kinds), `Eof` and `Unknown #error`, one token per tree-sitter token you keep, and the nodes with the tags the shared code reads: `#delimited-list`, `#block`, `#key-value`, `#separator`, `#mapping`, `#sequence`. Read the grammar's `node-types.json` first: hidden rules (`_name`) are not nodes in the tree, so their children are tokens in the parent.
2. **Crate** `crates/lang-<name>` (a workspace member by the `crates/*` glob). Cargo needs a manifest before `cargo xtask codegen` can write the real one: create `src/lib.rs` (empty) and a `Cargo.toml` of `[package]` and `name = "lang-<name>"`. Then write `lang.yaml` and run `cargo xtask codegen`; it generates `Cargo.toml` (the shared dependencies, `build = "../../build/lang-crate.rs"` which embeds `rules/*.yaml` and writes `generated`, the `static-grammars` feature) and `src/provider.generated.rs` (`pub fn provider() -> ParserProvider` filling a `core_treesitter::Spec`). Keys of `lang.yaml`:

   - `grammar-crate` and `grammar-version` (the tree-sitter crate: a workspace dependency of the root `Cargo.toml`, `optional` behind the default `static-grammars` feature; `grammar-default-features: false` for a crate whose defaults are unwanted); `grammar-path` instead of `grammar-version` for a fork in `grammars/tree-sitter-<lang>/`, see [../development/grammar-forks.md](../development/grammar-forks.md)), `language-const` (default `LANGUAGE`; the language is `core_packs::language!("<name>", <crate>::<const>)`), `inline-language-const` (a second grammar a pack exports as `sudsy_language_inline`).
   - `vscode-languages` (the language ids VS Code gives its files, real ids only: `javascript`, `shellscript`, ...), `extensions` and `file-names` (exact names such as `.editorconfig`; a trailing `*` matches a prefix, `Dockerfile.*`; `cargo xtask codegen` rejects an entry two languages share), `exclude-names` (file name patterns the extensions and names do not claim, `FilePattern::Except`: `*.h.cmake`, a template of another language; `ParserProvider::without`, only in the generated provider of a language with a `parse` key), `formatter` (the `NodeFormatter` type, re-exported from `lib.rs`).
   - Optional: `mapping` (below; a string names a hand-written `Mapping` instead, default `mapping::MAPPING`), `composite` (a map `text`, `continuation`, `tolerant` for a `Composite` with no injected grammar, see below; a string names a hand-written one), `hooks` (default `core_rules::DEFAULT_HOOKS`), `families`, `validate` (a function for semantic checks), `snippet-contexts` (pairs of text before and after; a pattern snippet is tried in them before the common contexts: Go `f(x)` outside a function parses as a conversion, so Go lists `func _() {` and `}`), `embedded` (finds code of other languages, see below), `options` and `presets` (below), `generate` (a data table built from npm packages by `cargo xtask generate <language> <npm dir>`: `output`, `header`, `sections` of JSON `file` sources with `at`, `prefix`, `not_prefix`, `except`, and the name normalization `strip_leading`, `cut_at`, `drop_prefix`; CSS is its only user, so it is a `lang.yaml` key read by `xtask/src/generate.rs`, not a row), `deps` and `dev-deps` (workspace dependencies beyond the shared ones).

   By hand: `src/format.rs` (`include!("schema.generated.rs");` for the option schema and its name consts, and a `NodeFormatter` for the nodes whose tag default is not right), `src/rules.rs` (`RULES`, the Rust rules; empty to start), optionally `src/hooks.rs` (`RuleHooks`: keys and scalars for the shared rules), and `src/lib.rs`: the doc comment, the `mod` lines, `pub use format::{..., option_schema};` and `include!("provider.generated.rs");` (which also holds the typed wrappers `generated`, written by the build script from the grammar).
   `options` is the formatter's option schema, in order, and `presets` the names of `presets/<name>.yaml` files (`<language>/<name>`); codegen writes `src/schema.generated.rs` (one const per option, an `OptId` (below), a typed getter per option declared in full: an enum with a `fn <name>(&ResolvedOptions)` for a choice whose values are plain words, `bool` or `usize` otherwise, never panicking, an absent option reads as its default; and `option_schema()` with the presets), which the crate includes where its formatter lives. An entry is `indent_style` or `end_of_line` (shared, no argument), `line_width: 80` (a shared option with its default; `max_blank_lines: [1, "doc"]`), or `name: {values: [...] | range: [min, max] | kind: words | kind: word-sets, default: ..., doc: ...}` (a choice, an integer, a word list, a list of word lists; with none of these a boolean). Hand-written languages (JSON, YAML, C#) have a `lang.yaml` of these two keys only. Options are read by id: `cargo xtask codegen` gives every option name an `OptId` (`core_config::opt::NAME`, `crates/core-config/src/opt_ids.generated.rs`) from the `options` of all `lang.yaml` files plus `crates/core-config/options.txt`, and `ResolvedOptions` is a vector indexed by id, so a read is an array access and a list value is borrowed (`strings(id)` iterates, nothing is copied). There is no read by name; where data names an option (a `format.rules` row's `option:NAME`, an `option_kinds` row) the name is turned into an id once at row parse (`core_config::opt::must`). **Shared code that reads an option no language lists in its `lang.yaml` (or that a hand-written schema builds, or code sets with `ResolvedOptions::set`) adds one line to `crates/core-config/options.txt`**; an `OptionDef` whose name is in neither list panics when its schema is built. `ResolvedOptions` has the shared readers for what the getters do not cover (`text`, `is`, `uint`, `flag`, `has`, `strings`, and `brace_on_new_line(element)` over the shared `brace_newline` and `brace_same_line` options of `core_config::shared`): code does not match on `OptionValue`. The policies of the shared shapes (`BinaryPolicy`, `ChainPolicy`, `AssignPolicy`, `ConditionalPolicy`) are built once per file: use `cx.binary_policy()`, `cx.chain_policy()`, `cx.assign_policy()`, `cx.conditional_policy()`, never `Policy::of(cx.options)` per node; per-file data a language derives from options goes through `FormatCtx::cached`. Validation beyond the declared kind is not expressed here: the schema has none today.
   `mapping` is a map from a grammar kind to the tree-sitter node names it takes (a list, or one string split on blanks; a keyword that shares its name with a rule is quoted, `'"message"'`): `Keyword: 'if then fi'`. `wrap: {Token: Node}` is `Mapping::wrap`; `checked: 'Token ...'` lists the tokens whose swallowed children are still checked for errors (XML); `same: 'table pair'` lists names whose kind is the same name in Pascal case (`table` is `Table`). Every grammar token with fixed text also takes the anonymous tree-sitter token of that text with no entry (`token LBracket "["`); an entry for the same name wins. Codegen writes the `Mapping` (and the `Composite` of a `composite` map) into `provider.generated.rs`. A table with logic (`lang-markdown`: injected grammars with closures) stays Rust in `src/mapping.rs`, named by string.
3. **Register**: nothing by hand. `cargo xtask codegen` fills the `generated:` regions (`# generated:NAME` ... `# /generated`) of the root `Cargo.toml` (grammar and language dependencies), `crates/languages` (dependencies, `static-grammars`, `providers()`), `crates/pack` (dependencies, features, `exports!`) and `scripts/pack.sh`, from every `lang.yaml` (see [language-packs.md](language-packs.md)) in two stages: `xtask` writes this glue (the regions, `Cargo.toml`, `provider.generated.rs`, `schema.generated.rs`, the node tables, the worker constants) from `lang.yaml` and the grammar files without compiling any language, so stale or missing glue never blocks it; then `xtask-full` (`xtask/full`, which depends on `languages`) writes what derives from the compiled providers (schema, docs tables, editor lists) and serves `cargo xtask affected`; `--check` runs both, stage 1 first, and fails until the regions are current. Nothing else names the language: the grammar registry (`core_syntax::grammars`) and the crate's `generated` module (kind constants, AST wrappers, the grammar hash) come from the build scripts, and the config schema, the docs' rule and option tables, the language lists of the README, the overview and the editor docs (`<!-- generated:languages -->`), and the VS Code activation events, document selector, keywords and description (`editors/vscode/package.json`, `editors/vscode/src/selector.generated.ts`, from the `vscode-languages` list of each `lang.yaml`, which holds real VS Code language ids checked against `xtask/full/data/vscode-language-ids.txt`, and the providers' file matchers) from `cargo xtask codegen`. Add `docs/ai/formatting/<name>.md` with a `<!-- generated:options -->` block. Shared comment rules and `max-line-length` work through the grammar tags with no code. `cargo xtask new-rule <name> <id>` needs the language's `starter.<Kind>.<ext>` ([../development/testing.md](../development/testing.md)).
4. **Pattern rules**: `crates/lang-<name>/rules/*.yaml` (no `language:` key) are built-in rules with no further code ([../rules/patterns.md](../rules/patterns.md)).
5. **Tests**: `tests/main.rs` lists the files as modules (`mod <name>; mod rule_fixtures;`; the generated `Cargo.toml` declares it as the `integration` test); `tests/<name>.rs` is a `fmt` helper over `provider_api::format_testing` (`assert_formats(provider, "a.ext", input)`: round trip, meaning, idempotency, comments kept; `Formatting` for a subject with options), `assert_file_names` for the file matchers, `check_corpus(provider, "a.ext", "<name>", &["ext"])` for the ignored conformance test, and one test per layout rule; `tests/rule_fixtures.rs` is the six-line copy of any other language's. The corpus fetch script in `tests/conformance/` (pinned commits, gitignored corpus) is `source tarball-corpus.sh` and a `fetch_tarballs <name>` list of `repo sha tar-pattern...` lines (copy `fetch-shell-corpus.sh`).
6. **Measure**: committed input files in `bench/inputs/<ext>/` (the folder is named after the files' extension; `perf-bench list` finds the provider by it, and `bench.sh` measures what it lists) (150 KB at most per language) and record parse and format throughput, binary size and build time in [../performance/numbers.md](../performance/numbers.md).
7. **Docs**: [overview.md](overview.md) (the parser row), the presets list, the roadmap. **Parity** with an upstream formatter: an entry in `scripts/parity_tools.json` ([../development/parity.md](../development/parity.md)). The format and lint legs are measured on a real-world group: 300 or more files of real projects, picked by project before any result is seen, never the tool's own test suite (that is ratcheted beside it); `groups` in `xtask/full/support.yaml` names it, and only that number counts for Ready. Both legs write their landing samples in the same step (`PARITY_WRITE=1 scripts/parity.sh format <tool>` for `landing.txt`), so the gate guards the language from its first landing on.

## After a language lands: the generalization step
Each new language should cost less code than the last. When a language's step 1 is on main (the crate, the parser or adapter, registration, harness), the lead gives one agent a step to shrink what the next language will have to write:
- Measure: `scripts/cost.sh <first>^..<last>` over the language's commits, per category, next to its nearest peers (same parser kind: tree-sitter, or an external parser behind an adapter such as oxc, ruff).
- Find code of the same shape across `lang-*` crates (adapters, provider glue, hooks, option schemas, test helpers, parity modes, corpus and bench scripts) and hand-written files that follow a template; move them into a core crate, into codegen from `lang.yaml`, or into a script, and delete the copies.
- Find the sinks: which kind of code grew most per language (formatter, rule fixtures, docs, generated data) and what would make it cheaper.
- Record the per-language numbers in the list below and land the extraction as one step (gate, finish, bench flat).

### Generalization of CMake
CMake's step put its layout into shared code from the start: `lang-cmake` holds 336 hand-written lines (lexer 140, parser 146, block table 19, glue 31), the block table, the 343-row signature table (generated from CMake's help) and `lang.yaml` values. What each shared piece costs a second user:
- `core_syntax::signature::Signature` (concept `command-signature`): two users, PowerShell's `missing-arguments` and CMake's layout. A third (a command table of another language) adds only rows.
- `shapes::keyword_call` (concept `keyword-sections`): one caller, CMake; it reads a plain `Signature` and the option `leading_argument_commands`, so it stays shared Rust with no rows. Candidates for a second caller are the languages whose call is a name with keyword sections after it: Dockerfile instructions (`HEALTHCHECK --interval=30s CMD x`, `COPY --from=x`), PowerShell cmdlet parameters (its table is the same `Signature` type, `-Name value` is a `Values::One` keyword) and shell command lines. None of them is laid out by keyword today, so none moves in this step; the first one that needs it adds rows, not code.
- `shapes::command_list` (concept `flat-command-list`): reads the block table and the signature table, so a second flat-command language (Makefile directives, `ifeq`/`endif`) adds a `Block` table.
- `core_syntax::block_pair` (concept `keyword-block-pairing`): single-use (`design/single-use.txt`); a candidate second user is Makefile conditionals (`ifdef`/`ifeq`/`else`/`endif`, `define`/`endef`); not built until the Makefile needs it.
In `lang-cmake` nothing is left that is a mechanism: the lexer and parser are the language's grammar facts (words, quoted and bracket arguments, `#[[ ]]` comments), the rest is data.

The adapters' step 1 is mostly the grammar file (one row per AST node kind, 200 to 250 lines), the adapter and the bench inputs; the formatter is the next sink. A new adapter language writes the kind table, the token mapping, the AST walk and a `parse_file`; the provider (about 100 lines each in JS, Python, SQL and YAML before), the tree replay (about 130 lines per adapter), the error constructor and the parse tests are shared.

- Rules that read names and scopes: the scope model and binder are shared (`core-semantics::scopes`); a language writes a table of rows by grammar kind (`scope.rows` next to `lang.yaml`, and `globals/*.txt`) that says which kinds open scopes, declare, read or write names and how a role passes to the children, and rules over the model that follow its reference tool (ESLint's and ruff's helpers differ in what counts as a read, a redefinition or a use, so the rule layer stays per language). Concepts a language needs that the table lacks are added as language-neutral row options (`global` / `nonlocal` redirects, class scopes hidden from nested functions, implicit declaration by a written reference). The `check` family over a table of `(name, node kinds, fn)` (`core_rules::checks::build`, `NodeCheck::hit`; JS, Python and CSS use it) and `FileCache<T>` are shared too.
- Code: grammar file about 40 lines, `lang.yaml` with the mapping about 40, formatter about 130 for TOML. Expect more formatter code for a language with irregular layout; the shapes cover lists, key-values, blocks and statement sequences.
- Cost in every build: a C compiler (already needed), the tree-sitter runtime once, and the grammar's `parser.c` and scanner per language; sizes are in `numbers.md`.
- Tree-sitter is 4-10x slower than the hand-written parsers and its trees need the adapter pass; the printer dominates the end-to-end cost anyway.
- A grammar that lags its language spec (TOML 1.1 today) needs a fork or an upstream fix, which the language then carries. Tree-sitter accepts documents that are syntactically fine and semantically invalid (duplicate keys, bad dates); the provider checks those after the parse and reports them as parse errors (`lang-toml/src/validate.rs`), so such a file is refused like a syntax error.
- Error recovery is tree-sitter's: a bad line may swallow a large span into one `ERROR`. The formatter refuses a file with errors, so this only affects messages.
- Not covered by the adapter: incremental reparse, a depth limit (the walk is iterative; the formatter recurses), dialects.

## Composite languages
A language made of several tree-sitter grammars (`lang-markdown`: the block grammar, and the inline grammar inside its `inline` and `pipe_table_cell` nodes) passes a `core_treesitter::Composite` to `core_treesitter::provider_of_composite`; the grammar file and the formatter stay one per language.
- `Injected { host, language, mapping }`: when the converter enters a node named `host`, it parses the node's text with the second grammar (`set_included_ranges`: the host range minus the host's own named children, which are the block continuations of quotes and lists) and scans the result with the second mapping in place of the host's children. The carved-out children are emitted as trivia where they fall. One parser pool per injected grammar; the second tree is dropped after the walk, so the cost is one extra parse per host node and a second mapping table.
- `text`: the kind of the token for text no mapped node covers, one token per line with its blanks trimmed; an unmapped leaf is then text, not an error. `continuation`: a `\` that ends a line (alone or after a blank) is whitespace trivia, not text (shell line continuations; `lang-shell` is a composite with no injected grammar). The converter tracks the end of what it has emitted and fills the gaps before each node and at each exit. `tolerant`: tree-sitter node names whose descendants' syntax errors are not reported (the text stays in the tree), for a language that turned tokens, which swallowed such errors, into nodes.
- `refine`: a mapped token whose text starts with a prefix is another kind (`<!--` makes an HTML block or tag an `HtmlComment`, a `#comment` token, so suppression comments and `no-empty-comment` work).
- Pattern rules match nodes only: wrap a token a rule needs in a node with `Mapping::wrap`.

## Embedded languages
Code of one language inside a file of another (shell in a Dockerfile `RUN`, the code of a Markdown fence) is parsed with that language's own provider and checked by its own rules; the host never re-reads it by hand. The host only says where the code is.
- A host declares regions with `embed <Kind> language "<name>" attribute...` rows in its grammar (`core_syntax::embed_rows`, the attributes are listed in that module's header): the node or token that holds the code (`in` its parent, `lead` words of the parent's first token, `named`, `root`, `dialect`, `when` text), the region (whole, `content`, `body` of a heredoc, `fence` lines of a fenced block, `after` a token kind, `trim`, `join` of several matches), the language (fixed, `info` word with `alias`, `attr` value) and the host's own parts inside it (`carve-lines`, `carve-end` with a file `directive`, `carve-line-start`, `carve-kind`, `carve-first`); `container <Node> marker <Token> [prefix "s"]` rows name the nodes whose content lines carry a prefix (`core_syntax::containers`, which the Markdown formatter reads too). `ParserProvider::embedded` runs the finder; any other provider implements `LanguageProvider::embedded`. An `Embedded` holds the language (a language name or a file extension, resolved by `provider_api::embedded::resolve` among the providers), the range in the host file, `carved`, `format` (whether the host lets the language's formatter rewrite the code), `strip` and `lint` (default true; `no-lint` when the host reads the tree itself and the language's own rules would be wrong for it: a Vue `<script>` region, where the `script` rule family binds the tree with `lang_js::bind_embedded` and the components' own checks run on that scope model). Examples: the `embed` rows of `grammars/dockerfile.grammar`, `makefile.grammar`, `markdown.grammar` and `html.grammar`.
- A host whose code sits at key paths of a data file (a workflow's `run:`) lists them in a `core_rules::embed_keys::KeyEmbeds` spec (paths with `*`, the keys that name the language with `$N` for what a `*` matched, a guess, the word-to-language table, the carved regex) and returns `embed_keys::find` from `LanguageProvider::embedded`; the regions of the file read last are kept, so the rules that read the host's own text do not search again; a region whose code no parser reads has the language `""`. One user so far, so it is a Rust spec and no grammar row.
- A data file whose structure is checked by key path (a workflow's keys, event names, permission scopes) lists `core_rules::shape::Row`s in a `Shape` (path with `*` and `a|b` alternatives, kind, allowed and required keys, names, a text format such as a cron line, `when` a key is or is not present, non-empty, unique keys) and gives each rule a `shape::check(&SHAPE, id, file, ctx)` body; the walk runs once per file for all the rules of the shape. One user so far, so it is a Rust table and no grammar row.
- The engine parses the range with the carved parts blanked to spaces (`Embedded::blanked`: same length, so an offset in the parse is an offset from the start of the range), or, when the host sets `strip` (Markdown: Python reads indentation, so a list item's prefix must not be in the code), without them; the findings are moved back with `Embedded::to_host`. A language nobody handles, a provider with a worker process (`embeddable()`), and code with syntax errors are left out: the code stays as written.
- Lint (`core-incremental`, the `lint` query): the embedded language's rules run on its parse with that language's config section (`FileInput::language`), its suppression comments, and the same path; positions, related spans and fixes are moved to the host file, and a fix that would touch a carved part or add a line break to a region with carved parts is dropped. The host's suppression comments apply to the result. Rules need no change.
- Host rules read the parses through `FileContext::embedded` (`EmbeddedTree`: range, language name, root): the Dockerfile `run-command` family reads the commands of a `RUN` from the Shell tree and checks them with `core_rules::commands` (the selection and the check are shared; the family finds the `RUN` and its exec form). A rule fixture run of such a host names the companion providers: `provider_api::fixtures::rule_fixtures_with(&host, &[&companion])`.
- Format (the `format` query): when the host's options do not turn it off (`embedded_language_formatting`, declared by the host's schema), each region with `format` is formatted by its language's formatter on the code without the carved parts, and put back with the first code line's host prefix on every line. This runs on the host's output, which is parsed again to find the regions; if the regions changed, the host's output stays. The host formatter itself never sees the other language: a host that does not set `format` (Dockerfile) keeps the code as written.
- A host whose regions never set `format` (`LanguageProvider::formats_embedded` false: Dockerfile and Markdown still walk, GitHub Actions says no) is not walked by `format`.
- A host that lays the code out itself (HTML: `<script>`, `style=""`) formats it through `FormatCtx::embed(language, mode, code, width, single_quotes)` (`core_format::Embedder`; the engine implements it for the `format` query, other callers pass none and the code stays as written). `mode` says what the code is: a whole file, one expression or a declaration list. The other language's provider reads the mode from `SourceFile::language_version` (its `parse` wraps the code: `[expr]` in JS, `a{ ... }` in CSS) and from the `embed_mode` option (its formatter prints the wrapped part only); `width` replaces its `line_width`, and `single_quotes` makes its strings prefer `'` where the host's own quote is `"`. The result is text without a final line break, which the host splits into lines (`core_format::embed`: blank lines and shared indentation of the code, template literals kept, the lines as `Doc`s). Host options the other formatter takes over go through `Forward { host, ids }` (resolved once per file, cached per language, mode, size and forwarded values). A host whose output holds other languages' code compares it in `NodeFormatter::embedded_check`, which asks `Embedder::same_code` (the other provider's tree and value comparison); a language that writes the code in continued lines (`EmbedMode::Continued`) is described in [../formatting/shell.md](../formatting/shell.md#continued-mode).
- Cost: a host that reports no regions pays one call returning an empty list; a region costs one parse of the other language, and its rules one run.

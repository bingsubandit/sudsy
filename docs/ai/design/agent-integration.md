# Plan: agent integration (benchmark, output, fixes, new findings, hooks, MCP)

Turns Sudsy into the cheapest checker for a coding agent to run, and measures it in a way that can
be published. Evidence for the choices: [agent-workflows.md](agent-workflows.md) (mock tools,
Haiku and Sonnet; hooks, one command and actionable messages were clear on both models).

What exists today: `sudsy check` (`format --check` + `lint`), `sudsy fix [--unsafe]` (applies fixes
until none is left, then formats, reports what remains), `sudsy rules <id>`, `init --agents` (the
agent block in `AGENTS.md`/`CLAUDE.md`, also a question of the interactive `init`), the LSP over the
incremental database, the pattern-rule engine `core-patterns`. Fix kinds (`core_rules::FixKind`):
`Safe` (applied by `fix`), `Unsafe` (by `fix --unsafe` and editor quick fixes), `Suggestion` (editor
only). The human output prints `path:line:col: severity[rule]: message`, `note:` lines and
`fix (kind): title`, but neither the source line nor the replacement text.

Order: the benchmark first (built; its first full run is the baseline every later step is measured against),
then the steps in the order of their measured effect per cost.

## Step 1: the agent benchmark (built; no full run yet)

The numbers we publish: what each Sudsy feature saves an agent, measured one feature at a time on real
tasks in real repositories, with intervals that repeat within a few percent. Built in
[`tools/agent-bench/`](../../../tools/agent-bench/README.md), run by `scripts/agent-bench.sh [--smoke |
--full] [--pairs E1,B,...]`. Not in CI: it costs money and needs a logged-in `claude`. The first full run
(the baseline of every later step) waits for the user's go-ahead; its numbers go to
`docs/ai/performance/agent-numbers.md` (latest values only), which that run creates.

### What is compared
- **Feature pairs, the main numbers** (`pairs.toml`, the pilot's experiments of
  [agent-workflows.md](agent-workflows.md) on real code). Both arms use Sudsy and differ in one feature;
  each pair runs on the tasks where that feature matters and is reported as its own ratio:

  | Pair | On | Off | Tasks |
  |---|---|---|---|
  | E1 | `sudsy hook post-edit` after each edit and `sudsy hook stop` at the end (`sudsy-hooks`, registered as `init --agents` does) | the agent runs `sudsy check` | 25 ordinary coding tasks |
  | E7 | `sudsy check` | `sudsy format --check` and `sudsy lint` as separate commands | 38: every task where the agent checks its change (ordinary, lint-debt with formatting damage, fix-id, long-report) |
  | E3 | the human report: source line and fix text under each finding | `--format concise`, one line per finding (the real flag) | the 6 lint-debt and 4 fix-id tasks |
  | E2 | `sudsy check --new`: only the findings the change added (`sudsy-new`) | every finding | 11 ordinary tasks whose files carry 3 or more old findings (click, flower, pathe) |
  | E8 | the report collapsed by rule above 100 findings | the full list (`sudsy-full`: the real `--rule` with every rule present) | 3 click tasks with 388 findings in the repository |
  | E3C | fix ids and `sudsy fix --apply ID` | ids removed and `--apply` refused (`sudsy-noids-provisional`) | 4 tasks whose findings carry suggestion fixes |
  | E10 | the project policy enforced by a pre-written pattern rule | the policy stated in `CLAUDE.md` only (`sudsy-norule`) | 4 ordinary changes that invite the violation |

  Both arms use real Sudsy commands, flags or config where they exist (`--format concise`, `--rule`,
  `--new`, `sudsy hook`); turning off a feature that has no flag is a thin shim (`wrap.py`) in front of the
  binary, and the arm's name ends in `-provisional` (E3C's off arm, the only one). The native hook arm
  (`native-hooks`, in B-hooks) runs `hook.py`: the repository's lint after an edit, its fix commands at
  stop.
- **Size.** From the spread of the first smoke batch (4 tasks per pair, 2 reps, Haiku; `stats.py` prints
  the estimate), the ±5% bar on turns and cost needs about 50 tasks at 5 reps for E1 (10 reps with its
  25), 15 for E3 (8 reps with its 10), 15 for B (5-6 reps with its 15), and 30-60 tasks for E7, E2 and
  E10, 15-30 for E3C and E8. E1, E3 and B reach the bar with the set as it is; E7 (38 tasks) is close;
  E2, E8, E3C and E10 need more tasks of their kind before their numbers can be published (open:
  about 30 more E2 and E10 tasks, 10-25 more E8 and E3C tasks). The estimate is re-read from the first
  full batch.
- **Stack comparison, secondary** (pair B, and B-hooks with both sides behind hooks): `native` (the
  repository's own commands) against `sudsy-matched` on the 15 ordinary tasks of the Python and
  TypeScript repositories. The Sudsy side's `configs/<repo>.sudsy.yaml` is generated by `matched.py`: the
  Sudsy rules the parity catalogs map to the rules the native config selects (resolved by the tool:
  `ruff check --show-settings`, `eslint --print-config`, oxlint's default set), every other rule of the
  language off, and only the files the native tools check. Each file's header lists the mapping and the
  native rules without a Sudsy rule (they stay on the native side): click 86 mapped / 70 not, humanize
  118 / 398, ufo 49 / 125 (most of them unicorn), pathe 46 / 66. chi is not in B: its native
  check is `go vet`, which no Sudsy rule mirrors.
- **Policies** carry no rule writing: the rule is in the start tree (E10's on arm), and the measured task is
  an ordinary change that tempts the violation (a decoded path helper next to `decodeURIComponent`, an
  origin helper next to `new URL`, an age helper next to `date.today()`, a cwd helper next to
  `process.cwd()`). The score is the violations that land, with turns and cost. The native equivalent of
  each rule is noted in its task (ESLint/oxlint `no-restricted-globals` or `-properties` for three; none
  for humanize's clock helper). Writing a rule is a one-time cost and is not in any ratio.

### Repositories and tasks
- **Repositories** (`repos.toml`), each pinned at a commit and cloned blobless by `fetch.py`: click and
  humanize (Python: ruff + ruff format, ruff + black), ufo and pathe (TypeScript: ESLint + Prettier,
  oxlint + oxfmt), chi (Go: `go vet` + `gofmt`), flower (the mixed repository: Python, Dockerfile,
  docker-compose, Prometheus and Grafana YAML, workflows; pylint, no formatter). Tool versions are pinned
  there (a venv per Python repository, `node_modules` from the pin's lockfile). The sudsy arms start from
  `sudsy init -y` with each repository's closest presets (`sudsy_init`), and the tree formatted by Sudsy.
- **Task set `tasks/v2/`**, 42 tasks (a new version of the set is never compared with an older one):
  23 bug fixes and features from real commits (the run starts at the commit's parent; the verifier puts
  the commit's tests in place), 2 refactors with same-name decoys, 6 lint-debt tasks (seeded findings and
  formatting damage, one per repository; flower's is its Dockerfile), 4 fix-id tasks (project pattern rules
  with suggestion fixes: `prefer-starts-with`, `len-zero`, `use-echo`), 3 long-report tasks (fix one rule's
  real findings in click, leave the rest), 4 policy tasks. Each task lists its pairs.
- **Verifier** (`verify.py`), with the arm's own tools: the task's tests, checks, clean files (lint debt:
  no finding of the named rules left), files that must end formatted, its policy rule (no new violation,
  scored with the rule added in a scratch copy, so both E10 arms are scored alike), nothing changed outside
  the scope, no new lint finding on the changed files and no changed file that was formatted at the start
  left unformatted. A finding is new unless the same (path, rule, line text) is in the start tree as often.
  A run succeeds when all pass; the other family's counts are recorded as mistake counters.
- **Validation** (`validate.py`, no subject, no cost): per task and start tree its pairs use (sudsy;
  native and sudsy-matched for B; sudsy-norule for E10) the setup works, the task's own signal fails on the
  untouched tree and the reference (the commit, `solution.patch` or `solution_edits`) passes. All 42 pass.

### Runs
- One instruction template (`instructions.md`) fills in the arm's commands, the tests, the allowed
  commands and, for the hook arms, one sentence on the hooks. `claude -p` with `--output-format
  stream-json --verbose` (the transcript stays in the batch's work directory), `--permission-mode
  default`, a scoped `--allowedTools` (file tools; the arm's checker programs with any arguments; its
  runner commands such as `python -m pytest`; read-only shell commands; never a bypass),
  `--setting-sources project`, `--strict-mcp-config`, `--no-session-persistence`, a per-run budget cap and
  timeout (`bench.lock.toml`). Denials are recorded per run.
- Run directories live in the build slot (`AGENT_BENCH_WORK` overrides), outside every checkout, so a
  subject never reads Sudsy's own `CLAUDE.md`; a verified run's tree is deleted (`--keep-runs` keeps it),
  its transcript and META files stay.
- Each record has the Claude Code version (checked against `bench.lock.toml`; the installed `claude` is
  used), the requested model and the exact model ids, the Sudsy binary, version, commit and `crates/` tree
  id, the task-set version, the task's pairs and the costs.
- **Paired and interleaved:** a batch plans, for the selected pairs, every task of each pair under both
  arms; a (task, arm) run that several pairs use runs once. Every round holds every planned run in a seeded
  random order. Smoke: 4 tasks per pair (a seeded sample) x 2 reps on Haiku; full: every task x 5 reps on
  Sonnet.
- Raw results: `data/<date>-<sudsy sha>[-smoke].jsonl`, one line per run, committed per batch;
  the transcripts of a published batch go out as a release asset.

### Statistics (`stats.py`)
- Per pair and metric (turns, output tokens, uncached, cache-read and cache-creation input tokens, cost,
  time): the ratio on/off of geometric means over the pair's tasks of the per-task means, with a 95%
  bootstrap interval (2,000 resamples of tasks, and of reps within each task). A ratio with at least 5
  tasks whose interval lies within ±5% of it is publishable; the others are not published.
- Success per arm with a Wilson 95% interval; mistake counters (unformatted, new findings, out of scope,
  policy violations, runs with denials).
- Size estimate per pair: from the batch's spread (within-task variance of log metric, between-task
  variance of the log ratio), the reps the bar needs at the pair's task count, or the tasks it needs at 5
  reps.
- `stats.py --compare A B`: the repeatability check; every ratio of each batch must lie in the other's
  interval. The first published batch runs twice on the same versions.

## Step 2: actionable output

Built except the message rewording (still open). How it works: [../config/cli.md](../config/cli.md).

- The human output (the one agents read) prints the offending source line under each finding, and
  for a fix its replacement: the edited text for a one-line edit (`fix (safe): replace with
  log.info(...)`), a short `-`/`+` pair for a multi-line one, capped at a few lines.
- `--format concise` for very long reports: the one-line form without source lines (CI logs).
- Rule messages say what to do. The texts of [rule-texts.md](../development/rule-texts.md) keep
  their split (`description` says what is reported); the editor and CLI message of a rule with an
  obvious fix names it ("use `x?.y`"). Done rule by rule, most frequent first by the parity corpora's
  counts; tracked by a list that only shrinks, like `undescribed.txt`.
- A long report collapses by default when it has more than about 100 findings: one line per rule
  with its count and first locations, the full list by `--rule` (E8: input tokens −21% to −38%).

## Step 3: fixes in one call

Built; how it works: [../config/cli.md](../config/cli.md#fix-ids). Two ids can collide (6 base-32 characters: about 1 in 2,000 with 1,000 ids in one report); `--apply` then applies both.

The E3 fix-by-id condition paid one call per fix; applying several in one call removes that.
- Every unsafe and suggestion fix printed gets a short id (a hash of path, rule, the text of the
  finding's line and the fix's index), stable across runs while the line is unchanged. No state is
  stored: `fix` relints and finds the fix by its id.
- `sudsy fix --apply ID[,ID...]` applies exactly those fixes (any kind, suggestions included), then
  formats; an id that no longer exists is reported with the current ones.
- Accept all is `sudsy fix --unsafe` (already there): every safe and unsafe fix. Suggestions stay out
  of accept all: a suggestion is one of several possible changes (the reason it is not unsafe), so
  it is applied only by id.
- The agent instructions say: run `sudsy fix --unsafe` unless a fix must be checked; the report
  after it lists only what needs a decision.

## Step 4: only new findings

Built; how it works: [../config/cli.md](../config/cli.md#only-new-findings) and [../editor/lsp.md](../editor/lsp.md). Open: project and directory findings of a changed file always count as new (only the file's own findings are linted at REV).

### How other tools do it
From documentation known to us at writing time; recheck each before citing it publicly.
- **Baseline files in the repository:** PHPStan (`phpstan-baseline.neon`: message, path and count),
  Psalm (`psalm-baseline.xml`), detekt and ktlint (XML baselines), SwiftLint (`--baseline`), ESLint's
  bulk suppressions (`eslint-suppressions.json`: counts per file and rule). State is a committed file
  that must be regenerated as code changes.
- **Todo configs:** RuboCop `--auto-gen-config` writes `.rubocop_todo.yml` (rules off per file).
- **Inline suppressions:** Ruff `--add-noqa` writes a comment on every current finding.
- **Diff filters outside the linter:** reviewdog (`-filter-mode=added|diff_context`), diff-cover;
  lint-staged lints the staged files whole.

### Design
- `--new[=REV]` on `lint`, `check` and `fix` (default `HEAD`): a finding is new unless the same
  finding exists in the file at REV. No state file: for each changed file Sudsy reads its text at REV
  from git, lints it in memory with the current config, and compares fingerprints (rule, the
  finding's line text without leading whitespace, its occurrence number among equal ones). Line
  shifts do not matter, an edited line's findings count as new. Unchanged files are skipped, so the
  cost is one extra lint per changed file.
- A file not in REV makes every finding new; no repository or an unknown REV is an error.
- `--new` prints nothing and exits 0 when no new finding is left, which is what makes the hooks
  silent.
- A committed baseline file (the PHPStan model) is deferred: git covers agents and pull requests;
  it is built when a user needs new-only checks without a usable base revision.
- **Extension:** the LSP keeps showing all findings by default (people edit with the whole file in
  view). A setting `sudsy.diagnostics.scope: all | new` uses the same comparison against `HEAD`, the
  text at `HEAD` cached per file until `HEAD` moves.
- **CI:** `check --new=origin/main` checks a pull request against its base.

## Step 5: hooks (built)

`sudsy hook <event>` reads the hook input JSON of the agent on stdin and answers in its protocol;
Claude Code first (the protocol the experiments used). Built as described below; the protocol was
checked against code.claude.com/docs/en/hooks on 2026-11-28 (fields, exit codes, the
`stop_hook_active` loop guard, `systemMessage` for the note; MultiEdit is no longer listed among the
tools there and stays in the matcher for older versions). Behaviour and latency:
[config/cli.md](../config/cli.md#agent-hooks).
- `sudsy hook post-edit` (PostToolUse, matcher `Edit|Write|MultiEdit`): lints the edited file with
  `--new`, never formats (formatting under the agent makes its next edit miss the text it holds).
  Clean: no output, exit 0. Findings: the step 2 output on stderr, exit 2, so the agent reads them in
  the same turn.
- `sudsy hook stop` (Stop): `fix` (safe fixes) and format on the files changed since `HEAD`
  (tracked and untracked), then `lint --new` on them. Clean: exit 0. Errors left: exit 2 with them,
  so the agent continues; when the input says the stop hook already ran in this stop, exit 0 with
  the findings as a note, so it can never loop.
- `init` writes the settings: the AI agents question (and `--agents`) also merges both hooks into
  `.claude/settings.json` (an existing file is merged with `json_edit.rs`, never overwritten; an
  existing Sudsy hook is left as it is), and the agent block says formatting is automatic.
- Other agents with hooks get their own event names behind the same command once their protocol is
  checked; the instructions-only setup keeps working everywhere.

## Step 6: MCP server

The tools an agent decides to call; the automatic part stays in hooks.
- `sudsy mcp`: an MCP server on stdio over one long-lived database, like the LSP, so repeated calls
  are incremental. A subcommand of the one `sudsy` binary, its code in a crate `crates/mcp` linked
  into the CLI the way `lsp` is (no second binary or release). SDK: measure the `rmcp` crate against a
  small own JSON-RPC loop (binary size, dependencies, startup of the other commands unchanged),
  pick the smaller that covers tools and their input schemas.
- Tools, each returning the step 2 text (compact text costs fewer tokens than JSON):
  - `check(paths, new)`: findings with fix ids, nothing when clean;
  - `fix(paths, ids | all)`: applies, formats, returns what remains;
  - `explain(rule)`: the `sudsy rules <id>` text;
  - `search(pattern, language, paths)`: structural search with the pattern syntax of
    `core-patterns` (also as `sudsy search` on the CLI), matches as `path:line: source line`;
  - `test_rule(rule_yaml, paths)`: compiles a pattern rule and returns its matches without
    writing it, for the "make that an enforced rule" flow (E9).
- **Distribution.** An MCP client launches a command and talks over its stdin and stdout, so every
  existing package serves:
  - installed (npm, PyPI, Homebrew, Scoop, winget, release binary): `{"command": "sudsy", "args":
    ["mcp"]}`, the same version and config as the CLI, hooks and editor;
  - not installed: `npx -y @sudsylint/sudsy@<version> mcp` or `uvx sudsy@<version> mcp` (the npm
    shim passes stdio through to the platform binary), a download on first launch;
  - `init` offers the config for the agents it detects (`.mcp.json` for Claude Code), the same merge
    rules as the hooks: `sudsy mcp` when `sudsy` is on the PATH, else the `npx` form pinned to the
    exact version, never `@latest`, so a release never changes a project's checks unasked;
  - to check before building: an extension API for VS Code to offer the bundled binary as an MCP
    server, and a listing in the public MCP registry.
- Name-aware search (`references` through the symbol index of [symbol-index.md](symbol-index.md),
  the case grep and patterns cannot decide) follows when the index covers the language.

## Measurement gates
- Step 1's first full run on the current release is the baseline: every feature pair, and the stack
  comparison.
- After each later step: a smoke run of the pairs it changes; the step lands when its own pair improves or stays inside its interval, and
  the others stay inside theirs.
- Before anything is advertised: a full run, twice, on the release that ships the feature.

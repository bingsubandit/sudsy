# Kotlin (`lang-kotlin`)

## Parser
[ktrs-parser](https://github.com/Hexay/ktrs) 0.5.1 (MIT OR Apache-2.0) with `ktrs-syntax`, pinned to the exact version in the root `Cargo.toml` (dependabot ignores them; a bump is a deliberate change of `grammars/kotlin.grammar` and `crates/lang-kotlin/src/adapter.rs`, followed by the conformance run). It is a port of the Kotlin compiler's PSI parser, so node and token names are the compiler's (`FUN`, `VALUE_PARAMETER_LIST`, `LONG_STRING_TEMPLATE_ENTRY`), the ones ktlint's rules are written over. `.kt` files are source files, `.kts` (Gradle Kotlin DSL, scripts) are scripts; the file id decides.

`adapter.rs` walks ktrs's flat tree once and hands tokens and nodes to the shared `replay`:
- a node is the row of `grammars/kotlin.grammar` named like its PSI type in Pascal case (`FUN` is `Fun`); a PSI type without a row is transparent;
- a token is ours by its kind: every keyword (hard, soft, modifier) is `Keyword`, strings are `StringTemplate` nodes of `OpenQuote`, `StringPart`, `EscapeSequence`, `$` / `${` entries and `ClosingQuote`, and other punctuation is the grammar token with that text;
- whitespace, comments and KDoc are `replay`'s gaps (`//`, nested `/* */`, a `#!` first line) and follow the shared attachment rule; KDoc is a `Comment` like the others, its structure is not in the tree;
- an `ERROR_ELEMENT` is an `ErrorElement` node and a parse error with ktrs's message; tokens the parser left out of its tree become `Unknown` tokens with an error.

What ktrs needs from its caller, done in the adapter:
- it requires `\n` line breaks: the text is normalized and every offset mapped back (`crs`, a binary search), so a CRLF file keeps its line breaks;
- it recurses once per nesting level and aborts the process on overflow, so the parse and the walk run on a thread with a 256 MB stack, and a scan refuses text nested deeper than 2,000 brackets or 2,000 prefix operators; it is exponential in nested annotation arguments (`@A(@A(...))`, 4 s at 22 levels), so more than 12 are refused; a panic is caught; a file over 16 MB is not parsed (all declared in the `limits` map of `lang.yaml`). All of these leave the file as one `Unknown` token and one error, which the formatter and the linter refuse.

Failure modes of the parser itself: it follows the compiler of Kotlin 2.4.20 and rejects the newest experimental syntax of the compiler's master (union types, `error` as a modifier); it is quadratic on a chain of tens of thousands of binary operators.

## Formatting
Layout is our own code over the lossless tree on the shared kit (`crates/lang-kotlin/src/format/`: `decl.rs` declarations, bodies and lists, `expr.rs` control flow, lambdas, operators, `format.rules` `[space]` token spacing), following ktlint's `ktlint_official` style:
- every node is its children one after the other (`seq`) with the `[space]` rows of `format.rules`; a line break the source has stays a line break and everything after the first one hangs one level, except after modifiers and annotations and for a closing `)` or `]` on a line of its own;
- the kit lays out what has a shape: bodies, blocks and `when` (`shapes::block`), argument and parameter lists (`shapes::delimited_list`: a function with `function_signature_wrap_min_parameters` parameters or a class with `class_signature_wrap_min_parameters` breaks one per line, a call keeps the break the source has between arguments, trailing comma per `trailing_commas`), `=` of properties and functions (`shapes::assignment`, value below the `=` when the line is too long), strings as written;
- blank lines: before declarations of a file or class body (not between consecutive properties or type aliases unless the second has a comment; a blank between or after the comments in front satisfies it), after the package, the imports and the file annotations; none after `{` or before `}`; empty braces stay as written (`{}`, `{ }`, `{` newline `}`); a block comment is re-indented only when it is KDoc (`#indentable-doc`);
- `rewrite.rs` is ktlint's code rewriting, done on the source before formatting (`rewrite_source`, the result is parsed again and checked against): import order (`core_rules::imports`: ASCII, `java.`, `javax.`, `kotlin.` last, aliases last, no duplicates; not when comments are among the imports), a trailing comma after the last entry of an enum with several entries or one per line (`;` goes on its own line), `{ return x }` and `{ throw x }` as function body to `= x`, a blank line between a `//` comment and the KDoc after it. The modifier order of ktlint is the shared `modifier-order` rule (`core_rules::modifiers`, row `[modifier-order]` of `format.rules`), run before the layout like the rewrites above; so are the `comment-space` rule (`//x` becomes `// x`) and the braces of the shared `curly` rule (`core_rules::curly`, options `format_rules: [curly]` and `curly_style: chain`): the branches of an `if`/`else` chain or the entries of a `when` that have none get them when another one has them, spans lines or would go past the line width, and so does the body of a loop on a line of its own.

Member chains are the shared `call_chain` in the `wrapped` style (`member_chain_*` options in `lang.yaml`): the accesses of a plain name path in front of the first call stay with the head (`kotlin.math.f()`), every later dot starts a line when the chain breaks (four dots or more, a break before a dot in the source, a lambda or argument list that breaks in a link other than the last, or a line that is too long), and a call after a `}` or `)` that ends a line stays on it (`}.toList()`). A class or object with `class_signature_wrap_min_supertypes` supertypes puts one per line (`shapes::heritage`). Class headers, member chains and `when` are `[layout]` rows of `crates/lang-kotlin/format.rules` (shapes `heritage`, `chain`, `cases`); the rest is Rust. Annotations of a declaration stand on a line of their own. A `when` with an entry that spans lines has a blank line between all entries, else none; the conditions of an entry stand on the lines the source has them, all at the level of the entry (`flat` row). A comment after the `{` of a block or lambda, or between `)` and `{`, moves to the first line inside it. A value of `+=` and the other compound assignments moves below the operator like one of `=`; a function with an expression body moves the body below `=` before its parameters wrap. The supertypes of a class go below the colon, as a group measured from the colon, when they do not fit or contain a break. A lambda, `=` of a property, an argument (`name = value`) or an assignment moves its value below the operator when it spans lines, except a lambda; a comment at the end of the line stays there.

Gaps against `scripts/parity.sh format ktlint` (named in [../design/shared-core.md](../design/shared-core.md#layout)), by what is left: ktlint rewrites that belong in a shared rewrite layer (`: Unit`, `;`, empty `()` of a class, `//x` and `/* c */` comments, `: Unit` added when `{ throw x }` becomes an expression body), binary operator chains use source breaks (no `binary_chain`), a value that ktlint moves below `=` while Sudsy keeps the call on the line (and the reverse: ktlint breaks both), the width of a chain that ktlint wraps before it moves the value, comments between `)` and `{`, blank lines in lambdas, `string-template-indent`; files ktlint leaves alone because it fails on them (stdlib builtins) cannot match.


## Rules
Pattern files (`crates/lang-kotlin/rules/ktlint.yaml`) for the ktlint rules that are about names and structure rather than layout: `no-wildcard-imports` (on), `no-unit-return` (on), `no-empty-class-body`, `package-name`, `class-naming`, `enum-entry-name-case`, `no-empty-file` (off). The shared `max-line-length` and `comment-space` cover two more. `unused-import` (on; ktlint `no-unused-imports`) is the shared scope rule on `src/scope.rs`: an import declares the last name of its path or its alias, every `ReferenceExpression` and infix function name is a use, a name in KDoc is a use, and imports of operator, delegate and destructuring functions (`getValue`, `plus`, `component1`) are never reported. The catalog `docs/ai/parity/ktlint.yaml` lists every ktlint rule with its status; the layout rules are the formatter's.

## Parity
`scripts/parity.sh format ktlint` (ktlint 1.8.0, `ktlint_official`, see [../development/parity.md](../development/parity.md)) over the 5,776 corpus files it can parse: the ratchet counts the files that match byte for byte (4,666 of 5,776, 81%; the rest differ by the gaps above); a second format changes no file and the safety check refuses none.

## Conformance
`bash tests/conformance/fetch-kotlin-corpus.sh`, then `cargo test --profile corpus -p lang-kotlin --test integration -- --ignored --nocapture conformance`: kotlinx.coroutines, ktor, nowinandroid, ktlint and the Kotlin standard library, `.kt` and `.kts` (6,632 files, 20 s in the `corpus` profile): every file parses without errors, prints back byte for byte and satisfies the trivia rule; the 322 compiler PSI parser test inputs (`testData/psi`) that hold deliberate errors are reported, not required to parse. An unclosed block comment is an error.

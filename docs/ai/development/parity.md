# Differential testing against upstream tools

`scripts/parity.sh <tool>` runs the upstream tool and `sudsy lint` on the fixtures in `tests/parity/<tool>/` and compares the diagnostics as `(rule, line, column)`. The upstream rule name is mapped to a Sudsy rule id through the catalog (`docs/ai/parity/<tool>.yaml`: the entries whose status is `rule <id>`; an entry that names several ids (`rule unused-variable, unused-parameter`) maps to the first, and the diagnostics of the others are compared as the first's); an upstream rule with no mapping is a mismatch. Every mismatch is printed (`only <tool>`, `only sudsy`) and the exit code is 1 when there is any. Run it from Git Bash.

Tools: <!-- generated:parity-tools -->`actionlint`, `angular-eslint`, `buf`, `checkmake`, `checkstyle`, `cmake-lint`, `eslint`, `eslint-jsonc`, `eslint-plugin-svelte`, `eslint-plugin-vue`, `graphql-eslint`, `hadolint`, `html-eslint`, `html-validate`, `htmlhint`, `ktlint`, `markdownlint`, `phpstan`, `psscriptanalyzer`, `revive`, `roslynator`, `rubocop`, `ruff`, `shellcheck`, `sqlfluff`, `sqlfluff-fixtures`, `stylecop`, `stylelint`, `stylelint-less`, `stylelint-scss`, `tflint`, `typescript-eslint`, `yamllint` (lint mode); `biome`, `buf`, `clang-format`, `csharpier`, `csharpier-xml`, `dotnet-format`, `gersemi`, `google-java-format`, `invoke-formatter`, `ktlint`, `php-cs-fixer`, `prettier`, `prettier-angular`, `prettier-css`, `prettier-html`, `prettier-js`, `ruff`, `shfmt`, `sqlfluff`, `taplo`, `terraform` (format mode, below).<!-- /generated --> Both modes install the tool at the catalog's `version` on first use and build the debug CLI; the install is data (see [Tool entries](#tool-entries)). yamllint is a pip package installed below `<target>/parity/yamllint-<version>/` (needs Python 3 and network).

## Fixtures
`tests/parity/<tool>/` holds one file per case plus the two configs that make the tools comparable: the upstream config (`.yamllint`) enables only rules Sudsy has an equivalent for, with the parameters Sudsy's rules take, and `sudsy.yaml` enables the matching Sudsy rules. A fixture is one file for every config, so the parameters must be the same for all cases. Fixtures where the tools legitimately differ are not included; those differences are recorded in the catalog entry's `gap`. Rules the formatter covers (yamllint `comments`) are off in `.yamllint`: they are tested as formatter output instead.

To add a case: add the file, enable the rule in both configs, run the script. To add a tool: add its entry to `scripts/parity_tools.json` ([Tool entries](#tool-entries)), a function to `scripts/parity_lint.py` that returns the upstream diagnostics as `{(rule, line, column)}`, and its fixtures.

## Differences lists
`tests/parity/<tool>/differences.yaml` records where Sudsy differs from the tool; the same file serves both modes of a tool.
```yaml
differences:            # each named difference once: <choice|gap>  <text>
  subst-indent: choice  multi-line `$(...)` keeps the source indentation
  for-no-in:    gap     tree-sitter-bash rejects `for x do`
files:                  # fixture key -> names; a lint key is `<file> <tool|sudsy>:<rule> <line>`
  corpus/bats-core/contrib/release.sh: subst-indent, array-indent
ratchet:                # a corpus too large to list: the least identical files; the group's name in `files` gives it a difference
  prettier-tests: 302
target-files:           # per ratchet group (`fixtures` for ungrouped files): the files of the target (all minus the intentional ones, tool-rejected included); the README table's denominator; the run prints the measured value and fails when it is stale
  prettier-tests: 1200
second-format:          # per ratchet group (`fixtures` for ungrouped files): the most files that may change on a second format
  prettier-tests: 0
refused:                # per ratchet group: the most files Sudsy's safety check refuses (an internal error, not a syntax error)
  prettier-tests: 0
intentional:            # only the lead or the user adds these: name -> invalid-input | tool-wrong
  subst-indent: tool-wrong
fixes:                  # gap name or lint rule -> one line: where and what to change (a name no longer in `differences` or `missed` fails the run)
  for-no-in: crates/lang-bash/grammar, accept `for x do`
measured:               # lint: {covered, total, main}: what the target counts and the main commit the measured tree is based on (written with `missed`)
missed:                 # lint: rule -> findings that count as missing, all of them, layout left after `sudsy format` included: covered + missed = total, or the run and codegen fail (`scripts/parity.sh coverage <tool>` checks it, `COVERAGE_WRITE=1` writes both)
  SC2086: 28
sets:                   # format with a gap list (clang-format): ranked cause sets, one line each (scripts/parity_gaps.py --steps --yaml); the queue shows the top
  - "spacing Rpar|Ident in Cast: +100 files, 1007 equal after it"
unclassified: 12        # format: most differing files of the ratchet groups that no `name:N` explains (a ratchet)
not-comparable:         # lint coverage: rule -> evidence that its findings change with what the corpus lacks; left out of the target and printed with their count in every run (Roslynator)
  RCS1130: compiler 0, driver 10
pins:                   # file -> pin of Sudsy's output for it, for the tool-wrong names (scripts/parity.sh --pin <tool> prints them)
  corpus/bats-core/contrib/release.sh: 3fa9c01d7e5b2a64
```
`choice` is intentional and documented (the `choice` names are the generated block `<!-- generated:differences:<tool> -->` of the language's `docs/ai/formatting` page, written by `cargo xtask codegen`); `gap` is unintended, to fix, and stays out of the user docs. A text with `: ` or ` #` in it is quoted. The run fails on a differing file that is not listed (outside the ratchet groups), a listed file that no longer differs (stale; a lint fixture run checks only the files it ran, the coverage run's corpus keys share the file), a name no file uses, a name that is not defined, and a ratchet group below its minimum; above it, the run prints the count to raise the minimum to. Format runs also format Sudsy's own output once more (Prettier is not involved: Sudsy must reach a fixed point on its own output) and count the files that change, per ratchet group (`fixtures` for the ungrouped ones); the run fails above the `second-format` maximum and prints the count to lower it to. A file the safety check refuses is not formatted, so it is in no second-format count: the `refused` maximum counts those files the same way (a bug that the guard caught; the target is 0). The target is 0 for every group, and no input is dropped to lower it. `PARITY_FILTER` lists the files that change. The report ends with the number of files per name, `choice` then `gap`, and the ratchet lines.

Every run (format, lint, coverage) prints one number, defined in [../design/parity-target.md](../design/parity-target.md): the **target** (the share a user of the tool can get from Sudsy; 100% means all of it), then the intentional groups with their counts and the count of every input filter (`skip`, `skip_with`, non-UTF-8 files, files the tool rejects or cannot read, findings left out). The target leaves out only the reviewed intentional cases; everything else counts against Sudsy. The `intentional` map gives a name one of two values: `invalid-input` (the file is excluded from the target; the tool rejecting it is the evidence) and `tool-wrong` (the tool's output changes meaning, drops content or is unstable). A `tool-wrong` file is pinned: `pins` holds the first 16 hex digits of the SHA-256 of Sudsy's output for it, so a later change to that output is printed as `REVIEW` and counts against Sudsy until the lead reviews it and pastes the new pin from `scripts/parity.sh --pin <tool>` (a format run that also prints the pins of the `tool-wrong` entries; the runner never writes them). A lint finding is pinned by its key (file, rule, line), so no hash is needed; a finding that moves is unlisted and counts. In a coverage run the target leaves out the findings of `wontfix` catalog entries and counts the findings of `formatter` ids as missing until the tool has a proof run. Every coverage run of a tool with `formatter` catalog entries is that run, not an option: it copies the corpus, formats the copy with `sudsy format` under the tool's preset, runs the tool again and prints the findings of `formatter` ids that remain; only those count as missing in the target. A file `sudsy format` rejects stays unformatted, so its findings remain. Two more keys of `differences.yaml` serve the target. A file the tool rejects is always `invalid-input`, with no entry needed: the target leaves it out, and every run prints the group with its count (a ratchet group also counts them as `rejected by <tool>`). When Sudsy rejects a file and the entry is `invalid-input`, the language's reference parser must reject it too: a format entry with `reference_parser` (`npm`, `version`, `script`: a Node script that exits 1 on a syntax error; Prettier's GraphQL files use graphql-js 16) is run on those files, and one it accepts is printed as a Sudsy bug and counts as `REVIEW`. `flags` names each reference-tool flag that turns a feature off (`--no-config`, `--skip-javadoc-formatting`, `ignore_trailing_blanks`, `skip_with`) with its reason; every run prints `flag <name> (gap): N fixtures` for it, N being the fixtures the flag applies to (the files it changed the result of, for `ignore_trailing_blanks`; the files skipped, for `skip_with`). In a lint coverage run the target needs the same line (the column is not compared; every `parse` of `scripts/parity_tools.json` has a `line`): a report on another line is missing. The target leaves out a finding that is a reviewed `tool-wrong` one, listed in `differences.yaml` as `<file> <tool>:<rule> <line>` under an `intentional` name. `scripts/parity.sh --test` runs the runner's tests (`scripts/test_parity.py`: a pinned file whose output changed, the filter counts, the `fix` command), part of the gate.

## The queue
`docs/ai/parity/queue.md` (generated by `cargo xtask codegen` from every `differences.yaml`, kept current by `codegen --check`) opens with the priority table and lists per tool the open work: the unclassified count with its share of the differing files, the `gap` names ranked by files, and for lint the rules ranked by missed findings, each with its `fixes:` note. In `files`, a ratchet group's names may end in `:N` (`real-world: scss-layout:300, comments`): N differing files have that name as their first cause, so classifying a group's files is writing those numbers; the files of a ratchet group without `:N` stay unclassified, and the run prints `unclassified: N of D` and fails when N rises above `unclassified:` (a ratchet: lower it when the run says so); a tool without the key only prints the count (set it). A gap that reaches 0 files is removed with its `fixes:` note (the run reports an unused name). A parity step reads the tool's section first, classifies before it fixes, keeps unclassified under 15% of the differing files, takes the items from the top and commits the regenerated queue with each landing.
The priority table has one row per leg (format or lint of a reference tool) under 85%, from data that exists, with no hand-set tags: now and findings or files needed (`measured`, or `ratchet` over `target-files` of the groups the README table uses for the leg, so the two never disagree; no `target-files` means not measured), the causes (`missed` rules, or `gap` names by files) largest first until the need is met, a rest no cause names as `unclassified`, and the commit measured on (lint). Weight: primary tool 4, `popular: true` secondary 1, other 0.25 (`primary` and `popular` are keys of `xtask/full/support.yaml`). Difficulty: per cause 1 when its rule is mapped in the catalog, else 3 (a new rule, a format gap, an unclassified rest). Score = weight x points to the bar / difficulty. Order: primary legs (weight 4) first, secondary legs after them, the score inside each group. A lint tool with a `measured` share under 85% that `support.yaml` does not list is a row of weight 0.25. A leg with `blocked: <reason>` in `support.yaml` is listed apart. Under the table, the new-language rows come from `xtask/full/languages.yaml` (header: scales, demand method; `src/newlang.rs`): per language its demand, parser cost and, per leg (format, lint), the one primary tool (the tool most users run, chosen by usage evidence kept in `why`; a list of tools fails codegen) with gain and the cost as named parts. Score of a plan (lint, format, both) = 4 x 85 x Demand x sum(Gain) / (20 x (Parser + sum Cost)); every plan is assumed to reach the bar, so everything it takes is in the cost: base 1.0, type worker +0.3, project or symbol index +0.2, each missing shared layout part +0.1, layout whitespace only -0.3, width +0.2, penalty +0.5; findings that need running user code and tool bugs are excluded from the target and no cost. A leg with no reference tool competes like any other (held to [no-reference-tool.md](no-reference-tool.md)); the six existing such legs are `retrofit` rows (parser paid, note "retrofit to no-reference-tool.md"). Demand is computed (`newlang::demand`) from the raw `gh` (GitHub Innovation Graph pushers) and `so` (Stack Overflow survey share) values of the entry (of a supported language: the `popularity` of its `support.yaml` row): per source `sqrt(x / top)`, the mean, floored at 0.1; a language of one source only gets the other estimated by the median ratio of the sources and its demand prints `~`. The table shows the top 25 rows by best score; the other entries follow in one line of names and scores (all stay in the file). A language supported with one leg missing is a row too (parser 0); a `deferred` leg has no row. A number written `"~0.6"` is an estimate and a score with one prints `~`: such a row may only be picked to measure it. Rule for a free slot, stated in the table because it cannot see who works on what: a primary leg under the bar with an agent on it counts as handled; the slot goes to a primary leg under the bar without an agent first, else to the best new-language row, before any secondary-tool work. The line under the table lists the primary legs under the bar (blocked ones excluded). Take work from the top of the table.

## eslint-jsonc
`scripts/parity.sh eslint-jsonc` uses ESLint 9 with eslint-plugin-jsonc (`docs/ai/parity/eslint-plugin-jsonc.yaml`; needs Node), copies `tests/parity/eslint-jsonc/` to `work/` there so that `eslint.config.mjs` finds the plugin, and runs ESLint on every `.json` fixture. A fixture's name selects the rule and options: `eslint.config.mjs` enables one rule per fixture and `sudsy.yaml` enables the matching Sudsy rule through `overrides`, so both sides stay in step. `sorted-keys` and `sorted-array-values` report the entries that would have to move; where several shortest edits exist ESLint's pick can differ from Sudsy's, so fixtures stick to cases both agree on (the catalog `gap` says so).

## markdownlint
`scripts/parity.sh markdownlint` uses markdownlint-cli2 (needs Node), copies `tests/parity/markdownlint/` (the `.md` fixtures and a `.markdownlint.jsonc` that turns on only the rules Sudsy has an equivalent for) below its install folder and compares `(rule, line)` of every fixture: markdownlint reports a column for some rules only, so columns are not compared. The Sudsy rule of a `rule:` status stands for the MD id of the catalog entry.

## hadolint
`scripts/parity.sh hadolint` runs hadolint with `-f json` and `sudsy lint` (config: `tests/parity/hadolint/sudsy.yaml`, `preset:dockerfile/hadolint`) on the rule fixtures of the Dockerfile rules, `tests/rules/dockerfile/*/*.dockerfile` with their annotation lines removed, so the fixtures are not copied. `(rule, line)` is compared for the rules the catalog maps; hadolint's other codes (deferred DL rules, ShellCheck) are ignored. The rule fixtures are written to agree with hadolint; a case where it deliberately differs goes into its [differences](#differences-lists) (the lint key form).

## shellcheck
`scripts/parity.sh shellcheck` is the hadolint mode for shellcheck, run with `-s bash -o all -f json` (the optional checks are in the catalog, so they are on) and compared as `(rule, line)` with `sudsy lint` under `tests/parity/shellcheck/sudsy.yaml` (`preset:shell/shellcheck`) on `tests/rules/shell/*/*.sh` without annotations.

## checkmake
`scripts/parity.sh checkmake` is the hadolint mode for checkmake, run with a JSON line template on `tests/rules/makefile/*/*.mk` without annotations; `sudsy lint` runs under `tests/parity/checkmake/sudsy.yaml` (`preset:makefile/checkmake`). checkmake runs all its rules on every file, so a fixture is compared on the rule of its own folder only (`(rule, line)`), and the two rules checkmake reports a line late (`timestampexpanded`, and `minphony` at the `.PHONY` line, which it reads as a variable) are moved back. Fixtures with a `<name>.rules.yaml` set rule options and are left out.

## ruff
`scripts/parity.sh ruff` is the lint mode for ruff: `ruff check --isolated --ignore-noqa --target-version py314 --select <the catalog's mapped codes> --output-format json` once on the rule fixtures (`tests/rules/python/*/*.py`, annotations removed) and the real-world projects of the format parity (`tests/conformance/fetch-python-corpus.sh`, fetched by the run; without the corpus only the rule fixtures are compared, about 120 findings against 445 with it), and `sudsy lint` (`tests/parity/ruff/sudsy.yaml`, `preset:python/ruff`, and every mapped rule turned on by the runner) on each file, compared as `(rule, line)`. The lint entry's `command` and `env` (`python -m ruff check ...`, `PYTHONPATH={prefix}`) serve the fixtures and the coverage run alike. `scripts/parity.sh format ruff` is the format mode (below).

## actionlint
`scripts/parity.sh actionlint` is the hadolint mode for actionlint, with the pinned corpus (`tests/conformance/fetch-github-actions-corpus.sh`: actionlint's own `testdata/ok`, `err` and `examples`, and the starter workflows). Each rule fixture (`tests/rules/github-actions/*/*.yml`, annotations removed) and each corpus file is copied to `.github/workflows/` of a work folder (a workflow is claimed by its folder), run through `actionlint -format '{{json .}}'` with the shellcheck and pyflakes integrations off, and through `sudsy lint`. An actionlint error becomes a catalog id from its `kind` and message (`actionlint_check` in `scripts/parity_lint.py`: `job-needs/cycle`, `expression/untrusted`, ...); the ids the catalog maps to a rule are compared as `(rule, line)`, the others are left out.

## psscriptanalyzer
`scripts/parity.sh psscriptanalyzer` uses the PSScriptAnalyzer module of invoke-formatter (`pwsh`: see invoke-formatter) and runs `Invoke-ScriptAnalyzer` (`scripts/parity_psscriptanalyzer.ps1`) with the catalog's `rule:` entries that the preset `powershell/psscriptanalyzer` turns on, on the PowerShell rule fixtures (`tests/rules/powershell/*/*.ps1`, annotations removed) and the corpus (`tests/conformance/fetch-powershell-corpus.sh`), compared with `sudsy lint` (`tests/parity/psscriptanalyzer/sudsy.yaml`, that preset) as `(file, rule, line)`. It also checks that the catalog lists exactly the rules of `Get-ScriptAnalyzerRule`. A lint key is `corpus/<path> <psscriptanalyzer|sudsy>:<rule> <line>` (a fixture is `<folder>-<name>.ps1`).
## stylecop
`scripts/parity.sh stylecop` copies `tests/parity/stylecop/` (a net10.0 project referencing StyleCop.Analyzers at the catalog's version, plus `.cs` fixtures) to `target/parity/stylecop-plain/` and `stylecop-fixed/`, enables every catalog SA id of status `rule:` or `formatter`, or `option: csharp.format.<name>` for an option the `csharp/stylecop` preset sets, as a warning through a generated `.editorconfig`, and runs `dotnet build` with an SARIF error log. Two comparisons:
- plain: each `rule:` SA id, mapped through the catalog, must be reported by `sudsy lint` at the same `(rule, line, column)`, and `sudsy lint` must report nothing else of the mapped rules;
- fixed: after `sudsy fix --unsafe .`, StyleCop must report none of those formatter ids whose coverage is `covered` (in any fixture) or `partial` (in the `layout_*` fixtures; the older fixtures show their gap), and what it still reports for `rule:` ids must match `sudsy lint`.
The fixtures' `sudsy.yaml` extends `preset:csharp/stylecop`, so the formatter ids are checked under the preset's options and the `rule:` ids with the rules the preset enables. The `layout_*` fixtures are the layout rules' violations; the `doc_*` fixtures (summary, tags, wording, text) are the SA16xx documentation rules' cases, valid C# in which every partial type has only parts that StyleCop and Sudsy judge alike (StyleCop accepts one documented part, Sudsy checks each); the run prints the formatter ids no fixture violates (the build would pass vacuously for them). Needs the .NET SDK and network for the NuGet restore. To add a case, add a `.cs` file and enable its Sudsy rules in the preset (`crates/lang-csharp/presets/stylecop.yaml`); the catalog drives the id mapping.

## Numbers

The target of every run (`scripts/parity.sh format <tool>`, `scripts/parity.sh coverage <tool>`; definitions in [../design/parity-target.md](../design/parity-target.md)). Format: identical files; coverage: findings the mapped rule reports on the tool's line. The ratchet `target:` of `differences.yaml` holds the coverage number; `cargo xtask codegen` copies them into [../parity/README.md](../parity/README.md), with the main commit each lint number was measured on (`measured.main`; `-` for a tool without one). The README table "Language support" is generated from the same ratchets (`xtask/full/src/support.rs`; the rows, language to reference tools, are `xtask/full/support.yaml`, with the language `ids` and the `speed` names of each row; the same rows feed the site's language pages and the package text, see [site.md](site.md)): format = `ratchet` identical files over `target-files` (the target denominator per group) summed over the tool's groups, lint = `target`; a tool without the numbers shows `not measured`.

`scripts/parity.sh stability <group>` is the format number of a language with no reference formatter (Dockerfile, Makefile, GitHub Actions, INI, EditorConfig, .gitignore): each file of the group's corpus (the `stability` entry of `scripts/parity_tools.json`: `fetch`, `corpus` as a coverage entry, `as`, `place`; the folders of the lint coverage runs) is copied alone into its own folder and formatted twice with `sudsy format` (a debug build, so the safety check runs). It is stable when it parses and formats without a refusal, the second format changes nothing and the summary line of the first has no `copied through` (more than half of the file text copied by `verbatim_node`, `verbatim_range` or a whole-file keep: `core_format::copied_through_files`, counted in `provider-api`'s `format_checked`). The run prints each file that is not stable with its reason, the share, and fails below `ratchet` (the least stable files, raised when the run says so) or when `target-files` is stale; both are per group in `tests/parity/stability/differences.yaml`, which the README table reads. No input is dropped.

The numbers themselves are in the generated pages [../parity/README.md](../parity/README.md) and [../parity/queue.md](../parity/queue.md) (covered, total, the main commit measured on, every cause); no other page repeats them.

## README groups
The README table reads the real-world groups of each leg (`groups` in `xtask/full/support.yaml`); the tools' own test suites (Prettier, Black, ruff, sqlfluff fixtures, PostgreSQL regress) are measured and ratcheted in `differences.yaml` but are not part of a README number.
A real-world corpus has at least 300 files, picked by project before any result is seen; files the tool rejects leave the target, files only Sudsy rejects count as missed.

## Landing check
A change to formatting code can lower a leg without any test seeing it; the parity legs are too slow for the gate. `PARITY_WRITE=1 scripts/parity.sh format <tool>` writes `tests/parity/<tool>/landing.txt` (`scripts/parity_landing.py`): 400 files of the pinned corpus (`tests/conformance/corpus`) that are identical to the tool's output, chosen in hash order of their path, each as `<16 hex digits of the output's hash> <path>`; a fall of 0.5% of the files is seen with about 85% probability. A leg whose comparison is not byte equality (`wrap_compare`: clang-format) or that has no pinned corpus has none. The hash is of the text the leg compares (`ignore_trailing_blanks` applied). `scripts/parity.sh landing [<tool>...]` formats the sampled files with the leg's own `sudsy.yaml` (and `sudsy_command`, styles, `copy_as`, `copy_suffix`) in one run per folder and compares the hashes; it needs no reference tool. A failure lists the files and says that a wanted difference is recorded by running the leg again with `PARITY_WRITE=1` (the sample is rewritten from the files that are identical then, so an improvement never makes it stale). An absent corpus fails when `CI` is set and is skipped with the fetch scripts named elsewhere. `gate.sh` runs it when `cargo xtask affected` selects the `landing` step (`core-format`, `core-syntax`, `core-rules`, `core-patterns`, `core-flow` or a language crate); with `CI` set it first runs the fetch scripts of the legs (`parity_landing.py --fetch`), and `finish.yml` caches the corpora (the key is the hash of the fetch scripts; `nightly.yml` fills it on the default branch).

The lint counterpart: `COVERAGE_WRITE=1 scripts/parity.sh coverage <tool>` also writes `tests/parity/<tool>/landing-lint.txt` of a lint leg whose coverage run has a pinned corpus: up to 150 corpus files as `<16 hex digits of the hash of Sudsy's sorted (rule, line) findings of the mapped rules> <path>`. Candidates are the files where every finding of the tool that counts is covered and Sudsy reports no extra finding of a mapped rule; 3 files per mapped rule with findings come first (rare rules first), then files with no finding up to 30% of the sample, then the rest, all in hash order of the path. A leg with fewer than 50 agreeing files is filled up with files in the state Sudsy reports today (the run prints which). `scripts/parity.sh landing` checks each with one `sudsy lint` in a folder holding the sampled files under the leg's preset (and `overrides`), no reference tool; a failure lists the files and says that `COVERAGE_WRITE=1` records a wanted change. An absent corpus is handled as for format. Legs that need the C# worker (StyleCop, Roslynator) and RuboCop have no sample.

## Nightly
`.github/workflows/nightly.yml` (daily 02:17 UTC, and `workflow_dispatch`) runs every parity tool of `scripts/parity_tools.json` and every language crate with ignored conformance tests, so a broken ratchet (`ratchet` minima, `second-format` and `refused` maxima, a new mismatch) or a broken corpus test fails without a person. `scripts/ci-nightly-matrix.py` builds the job matrix: one job per tool (`scripts/parity.sh [format] <tool>`; a lint tool also gets `parity-coverage-<tool>`, `scripts/parity.sh coverage <tool>`, the ratchet of the target and of the missed findings; a lint tool without fixtures passes its fixture job trivially) and per crate (`scripts/conformance.sh lang-<x>`: the fetch script, then `cargo test --profile corpus -p lang-<x> -- --ignored` minus the measurements `measure_startup_cost`, `scaling` and `model_cost`; `#[ignore]` reasons with "measurement", "prints timings" or "flaky" do not select a crate). A new tool or crate joins by existing; nothing is listed twice. Jobs do not stop each other and carry the tool's or crate's name. Tools (`target/parity`, keyed on the pins in `parity_tools.json`, `docs/ai/parity/*.yaml`, `jre.sh`, `dotnet-tools.json`) and corpora (`tests/conformance/corpus`, keyed on the fetch scripts, which update a stale cache by commit) are cached per job; the Cargo cache is saved from the default branch only. A cache is saved only by a passing job.

## Rule inventory
`scripts/parity_inventory.py <tool>|--all [--write]` compares a lint catalog with the rules of the tool's pinned version (the catalog's `version`): an npm plugin loaded by Node (ESLint and its plugins, stylelint and its plugins, html-validate, htmlhint, markdownlint), `ruff rule --all` from the PyPI wheel, the files of a wheel (yamllint, sqlfluff) or a raw file at the tool's tag (Roslynator's `Analyzers.xml`, tflint's and hadolint's rule lists). It prints the counts and the catalog ids the tool lacks, and with `--write` appends the missing rules to `entries:` as `planned` (deprecated: `wontfix`, ruff preview: `deferred`); `cargo xtask codegen` then regenerates the counts. Sources are the `SOURCES` table of the script; a tool without one (shellcheck, checkstyle, ktlint, StyleCop, actionlint, buf, PSScriptAnalyzer and the formatters) is listed by hand or by its own parity run. It needs Node and network.

## Coverage mode
`scripts/parity.sh coverage <tool>` measures what a team that switches would lose: the tool's default or recommended set runs on its real-world corpus and the result is the share of its findings that the mapped Sudsy rule also reports on the same line of the same file (`parity_lint.py <tool> ... --coverage`). A finding counts as covered when `sudsy lint` with the preset that mirrors the tool's default set (the tool entry's `preset` in `scripts/parity_tools.json`: `python/ruff`, `js/eslint-recommended`, `yaml/yamllint`, ...; a pure config file that lists the mapped rules of that set) reports the Sudsy rule the catalog maps its rule to on that line of that file and, when the upstream message quotes a name (`` `os` ``, `'x'`) and the Sudsy rule's messages do too, a message with the same name; the column is not compared. A rule with no mapping is uncovered. The report lists the rules with most uncovered findings (a mapped rule with 0 covered misses it or is not in the preset; one marked `no Sudsy rule` is unmapped) and ends with the target (the usability bar is at least 85%); the run fails when the target is below `target:` in the tool's `differences.yaml` (a ratchet, only raised: the run says when to) and `cargo xtask codegen` copies the number into the table of [../parity/README.md](../parity/README.md). A tool whose corpus is absent ends with `corpus absent` and the fetch scripts, exit 1, `target:` untouched (never "0 of 0"). A finding the tool reports at line 0 (no line) is covered only by a file-level report (one that starts at the first character) of the mapped rule in the same file. Fixture runs (`scripts/parity.sh <tool>`) compare `(rule, line)`.

## Tool entries
A tool is an entry of `scripts/parity_tools.json`, under `lint` or `format` (`parity_format.prepare` serves both modes), so installing one is config only (plus its `tests/parity/<tool>/` folder with `sudsy.yaml` and its `docs/ai/parity/<name>.yaml` with the pinned `version`):
- `catalog`: the catalog file whose `version` pins the tool (`version_command` instead: the SDK's own, for `dotnet-format`); `install`: an `npm` package (`with`: more packages), a `pip` package, a `dotnet-tool`, a `psmodule`, a `jar` (a Maven Central jar with its `sha256`, run with the pinned Temurin JRE that `scripts/lib/jre.sh <dir>` installs next to it, checksum verified; the runner writes a launcher script as the `exe`) or a `release` (URL template, per-platform `assets`: a zip or tar archive, a gzip or the executable itself) and its `exe`, installed into `<target>/parity/<catalog>-<version>/` on first use (a lint entry may name a format entry whose install it shares: `"install": "buf"`);
- `version`: the tool's release when the catalog pins something else (tflint: the ruleset's version);
- `needs`: `worker` builds the C# worker; `fetch`: scripts that fetch corpora;
- `coverage`: the entry of the coverage mode, run by `scripts/parity_coverage.py` for every tool without code of its own in `parity_lint.coverage`: `corpus` (`dir`, `glob`, `skip`; `as` or `into` name where the files go in the work folder), `command` (`{exe}`, `{prefix}`, `{python}`, `{work}`, `{root}`, `{group}`, `{files}`; without `{files}` it runs once per group), `group` (a regex whose first group splits the files into runs, `cwd: group` runs one in the folder of its name), `chunk`, `timeout`, `memory_gb`, `ok_codes`, `env`, `stream` (`stderr` where the report is there), `files` (config files written into the work folder), `group_files` (config files written into the folder of each group, `{group}` and `{prefix}` replaced), `parse` (`format` `regex` with named groups `file`, `rule`, `message`; or `json`/`jsonl` with `levels`, the lists to walk, and `file`, `rule`, `message` as `<level>.<key>.<key>`; `rule_prefix`, `rule_sub`, `rule_message` (message pattern to the id a finding is reported under), `rule_fn`, `json_line`), `map_also` (catalogs whose mapping also applies: hadolint runs ShellCheck), `instruction` (`rule_prefix`, `continuation`: findings whose code starts with the prefix count as covered when Sudsy reports the same rule on any line of the instruction that starts at the tool's line, an instruction going on while a line ends with `continuation`; hadolint reports ShellCheck codes at the first line of a `RUN`, ShellCheck at the line of the command), `overrides` (the `overrides` of Sudsy's config, for settings the tool gets from its own flags: sqlfluff's `--dialect` per folder), `unreadable` (rules that mean the tool could not read the file) and `sudsy` (`extends`, or `mapped_rules: <language>`). The tool reports into files, not pipes: a Node tool that exits after a write cuts a pipe at 64 KiB.

## Speed
`scripts/speed.sh [<tool>...]` ([plan](../design/speed-comparison.md)) measures the entries that have a `speed` key (one object, or a list: one per language), run by `.github/workflows/speed.yml`; a tool with no parity run (oxlint, dprint, `biome-js`) is an entry of the `speed` section, with no `command` and no `coverage`. A tool with a format and a lint entry carries the key on the format entry. The key:
- `language` and `label`: the README table.
- `corpus`: a name of the `corpora` section (`text`, `copies`, `fetch`, `sources` as fixtures); `{"group": <ratchet group of the entry's fixtures>, "text": ...}` (`fixtures` is the ungrouped ones); or `{"coverage": true, "text": ...}`, the corpus of the lint entry's coverage run.
- `format` and `lint`: the tool's check commands, run in the corpus copy (`c/` below the work folder, with Sudsy's `sudsy.yaml` above it). Placeholders: `{prefix}`, `{exe}`, `{python}`, `{root}`; an argument `{files}` is every corpus file, 500 per process. `"lint": "coverage"` runs the coverage command of the lint entry (its `files` and `env` too) on the same files.
- `preset` (format; a name or a list) and `lint_preset`: the Sudsy side's mirroring preset. Without them the format run uses `tests/parity/<sudsy or the tool>/sudsy.yaml` and the lint run the preset of the tool's lint entry; with none, the row is `not measured: no mirroring preset`.
- `not_measured`: `{"<task>": "<reason>"}`, a task that cannot run here (no install, no run, no row of numbers). A tool whose setup or run fails gets the same row with the error.
- A Sudsy run that crashes, exits above 1 or reports `0 file(s) checked` fails its row (`not measured: run failed`): a time without files is a wrong folder or preset, not a result.
- `env` (`{prefix}`) and `files` (config files written into `{prefix}`).

Example: `"speed": {"language": "Python", "label": "ruff", "corpus": {"group": "real-world", "text": "the Python corpus"}, "format": ["{python}", "-m", "ruff", "format", "--check", "--isolated", "--no-cache", "."], "lint": ["{python}", "-m", "ruff", "check", "--isolated", "--no-cache", "."]}`. A Sudsy run that exits with an error stops the tool's row. Output: `bench/speed.json`; `cargo xtask codegen` writes the README table from it.

## Format mode
One runner (`scripts/parity_format.py`) serves every format tool; an entry also has:
- `command`: the tool's command line with `{prefix}`, `{exe}`, `{python}`, `{root}`, `{group}` and `{file}` (a Python tool runs as `{python} -m <tool>` with `env` `PYTHONPATH={prefix}`; there are no wrapper scripts, only the PowerShell tools have one: no `pwsh` command line exists); `env`: variables of the run (`{prefix}`); `group`: a regex over the fixture's name whose first group is `{group}`; `input`: `arg` (the file name is an argument), `stdin`, `in-place` (the tool rewrites a copy) or `batch` (one run over copies of all fixtures, for a tool that starts slowly; `reject`: a regex over the tool's output whose first group names a file the tool rejects); `tool_may_reject`: a file the tool rejects is a difference, not an error; `reject_output`: for an `in-place` tool, a regex over its output: exit status 1 without a match is not a rejection (sqlfluff `fix` exits 1 when unfixable findings such as `LT05` remain, the file is fixed all the same; a `PRS` or `TMP` finding is the rejection); `generated`: `{lang}`, the crate whose `lang.yaml` lists the tool's generated-file markers (`generated_names`, `generated_header_markers`; the formatter skips by the same list): a matching file is left out and counted as `generated` in the input filters;
- `style_list` (a fixture source with a `style`; clang-format `ForEachMacros`): `file`, `key` and `option` name a list in a file of the source's corpus, added at run time to the style's tool file (`key:`) and to its `<style>.yaml` (`option`), so the corpus's own list is not checked in; a missing corpus file stops the run.
- `wrap_compare` (clang-format): compare the outputs token by token and gap by gap, ignoring line wrapping (`scripts/parity_wrap.py`; its `note` is printed by the run). The tokens and the gaps between them come from `sudsy debug tree` on both outputs; a gap inside one statement, declaration or directive is a wrap point (a newline equals a space, the indent is free); every other gap is exact: newline count, braces, spacing, comments, the statements of a macro body (after `;`, `{`, `}` outside parentheses) and the text between `clang-format off` and `clang-format on`. The ratchets count the files equal under it; the run prints byte-identical files, files with more over-long lines than the reference (not judged), the first cause of each difference, and with `PARITY_CONTROLS=1` the controls (the untouched source, damaged copies: wraps, blank lines, a string literal changed or split; another brace and pointer style). A run of adjacent string literals that clang-format made by splitting one (`BreakStringLiterals`) is read as the one literal: both sides are re-read with each run of such literals written as one, when the runs are equal in order, prefix and joined contents (byte for byte), outside a directive and outside `clang-format off`, and the reference tool's count of literals in the run is not the source's (a source of two literals that Sudsy joined is a difference). A damaged copy never has a block left of column 0 (when its anchor line is joined to a less indented one, the wrap gaps of that line stay), and a byte order mark is not part of the dumped text (offsets exclude it); the wrap-only controls are equal for every file. `PARITY_KEEP=<dir>` writes both outputs of each file. `PARITY_GAPS=1` adds to `wrap-<label>.json` every differing gap of every differing file (cause, kinds of the two tokens, parent kinds, the blanks of both outputs; the first differing token pair when the tokens differ). `scripts/parity_gaps.py wrap-<label>.json` ranks the causes by files and by greedy sets (`--steps`: the cause that finishes most files, each step with the files equal after it), answers how many files become equal when exactly some causes are fixed (`--fix field=a|b,...`, `--assume` for the ones fixed before) and prints the `files:` classification (`--classify`: the named gap of each file's first gap, `gap_name` holds the rules); the `sets:` list of the tool's differences.yaml is its `--steps --yaml` output, shown in the queue.
- `fixtures`: sources of fixtures, each a `dir` (default: the tool's folder) with `suffixes`, a fixture-name `prefix`, `recursive`, `nested` (copied with its folders, not flattened: the place selects the language or dialect), or a `list` file with `starts`; `kind: editorconfig-cases` is the `dotnet-format` layout below.

`scripts/parity.sh format prettier|biome` formats every JSON and YAML fixture in `tests/parity/<tool>/` with the tool (`prettier --no-config --no-editorconfig --embedded-language-formatting=off`, `biome format` with its defaults) and with `sudsy format`, and compares the outputs byte for byte. The tool is installed with npm at the catalog's `version` into `target/parity/<tool>-<version>/` on first use (needs Node and network); the fixtures are copied to `target/parity/<tool>-work/` first because `sudsy format` writes in place. The folder's `sudsy.yaml` extends the matching presets (`json/prettier-compat` and `yaml/prettier-compat`; `json/biome`), so a difference is a preset or formatter gap. Every difference is printed as a unified diff and the exit code is 1.

The `prettier` fixtures also include GraphQL: the folder's `.graphql` files and the corpus of `tests/conformance/fetch-graphql-corpus.sh` (`graphql/<repo>/<path>` in `differences.yaml`; Prettier's own tests in it include files it rejects, which count as differences unless listed, `tool_may_reject`). The `prettier` fixtures also include the folder's `.md` files, the repo's `docs/**/*.md` and the dotnet/runtime coding-guidelines docs (`tests/conformance/fetch-markdown-corpus.sh`, pinned); Prettier runs with `--embedded-language-formatting=off`, and the folder's `sudsy.yaml` sets `embedded_language_formatting: off`, because Sudsy's formatters of the fenced languages make other choices than Prettier's.

Fixtures that differ are listed in the folder's `differences.yaml` ([below](#differences-lists)). Fixtures named `crlf.*` keep CRLF line endings (`.gitattributes`: `-text`).

## sqlfluff
`scripts/parity.sh format sqlfluff` installs sqlfluff at the catalog's `version` (`docs/ai/parity/sqlfluff.yaml`, pip, into `<target>/parity/sqlfluff-<version>/`; needs Python 3 and network), fetches the SQL corpus (`tests/conformance/fetch-sql-corpus.sh`) and runs `python -m sqlfluff fix --rules layout,capitalisation` (the entry's `command` and `env`; a file with a parse error exits 1, so it counts as rejected) against `sudsy format` under the folder's `sudsy.yaml`. The dialect is the start of the fixture's name (`<dialect>__<name>.sql`: the `prefix` of its source), which both sides read: the entry's `group` (a regex over the fixture name whose first group is `{group}` in the command) for sqlfluff and `overrides` for Sudsy. The fixtures are the ratchet groups `sqlfluff-ansi`, `-postgres`, `-mysql`, `-tsql` (sqlfluff's dialect fixtures) and `postgres-regress`; the differences are all gaps (see [../formatting/sql.md](../formatting/sql.md#parity)). Every sqlfluff run (format, lint coverage of the real-world corpus and of the fixtures) passes `--config tests/parity/sqlfluff/reference.cfg`: `large_file_skip_byte_limit = 0` (sqlfluff's default 20000 skips a larger file, so format saw it unchanged and lint saw no findings) and `runaway_limit = 100` (default 10 stops `fix` early). Of the 79 differing files of 20-60 kB, a second `fix` changes 5 (`LT05` wraps one more nesting level per run: kestra `baseline-postgres.sql`, sqlserver-kit `dbo.sp_BenchmarkTSQL.sql`, `dbo.sp_WhatsupQueryStore.sql`, `dbo.usp_Generate_Merge.sql`, First-Responder-Kit `sp_AllNightLog_Setup.sql`); they are the gap `fix-loop-limit`. Larger files were not checked.

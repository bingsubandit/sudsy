# Differential testing against upstream tools

`scripts/parity.sh <tool>` runs the upstream tool and `sudsy lint` on the fixtures in `tests/parity/<tool>/` and compares the diagnostics as `(rule, line, column)`. The upstream rule name is mapped to a Sudsy rule id through the catalog (`docs/ai/parity/<tool>.yaml`: the entries whose status is `rule <id>`; an entry that names several ids (`rule unused-variable, unused-parameter`) maps to the first, and the diagnostics of the others are compared as the first's); an upstream rule with no mapping is a mismatch. Every mismatch is printed (`only <tool>`, `only sudsy`) and the exit code is 1 when there is any. Run it from Git Bash.

Tools: <!-- generated:parity-tools -->`actionlint`, `buf`, `checkmake`, `checkstyle`, `eslint`, `eslint-jsonc`, `eslint-plugin-svelte`, `eslint-plugin-vue`, `hadolint`, `html-eslint`, `html-validate`, `htmlhint`, `ktlint`, `markdownlint`, `phpstan`, `psscriptanalyzer`, `rubocop`, `ruff`, `shellcheck`, `sqlfluff`, `stylecop`, `stylelint`, `stylelint-less`, `stylelint-scss`, `tflint`, `typescript-eslint`, `yamllint` (lint mode); `biome`, `buf`, `clang-format`, `csharpier`, `csharpier-xml`, `dotnet-format`, `google-java-format`, `invoke-formatter`, `ktlint`, `php-cs-fixer`, `prettier`, `prettier-angular`, `prettier-css`, `prettier-html`, `prettier-js`, `ruff`, `shfmt`, `sqlfluff`, `taplo`, `terraform` (format mode, below).<!-- /generated --> Both modes install the tool at the catalog's `version` on first use and build the debug CLI; the install is data (see [Tool entries](#tool-entries)). yamllint is a pip package installed below `<target>/parity/yamllint-<version>/` (needs Python 3 and network).

## Fixtures
`tests/parity/<tool>/` holds one file per case plus the two configs that make the tools comparable: the upstream config (`.yamllint`) enables only rules Sudsy has an equivalent for, with the parameters Sudsy's rules take, and `sudsy.yaml` enables the matching Sudsy rules. A fixture is one file for every config, so the parameters must be the same for all cases. Fixtures where the tools legitimately differ are not included; those differences are recorded in the catalog entry's `gap`. Rules the formatter covers (yamllint `comments`) are off in `.yamllint`: they are tested as formatter output instead.

To add a case: add the file, enable the rule in both configs, run the script. To add a tool: add its entry to `scripts/parity_tools.json` ([Tool entries](#tool-entries)), a function to `scripts/parity_lint.py` that returns the upstream diagnostics as `{(rule, line, column)}`, and its fixtures.

## Differences lists
`tests/parity/<tool>/differences.yaml` records where Sudsy differs from the tool; the same file serves both modes of a tool.
```yaml
differences:            # each named difference once: <choice|gap>  <text>
  subst-indent: choice  multi-line `$(...)` keeps the source indentation
  for-no-in:    gap     tree-sitter-bash rejects `for x do`
files:                  # fixture key -> names; a lint key is `<file> <tool|sudsy>:<rule> <line>`
  corpus/bats-core/contrib/release.sh: subst-indent, array-indent
ratchet:                # a corpus too large to list: the least identical files; the group's name in `files` gives it a difference
  prettier-tests: 302
target-files:           # per ratchet group (`fixtures` for ungrouped files): the files of the target (all minus the intentional ones, tool-rejected included); the README table's denominator; the run prints the measured value and fails when it is stale
  prettier-tests: 1200
second-format:          # per ratchet group (`fixtures` for ungrouped files): the most files that may change on a second format
  prettier-tests: 0
refused:                # per ratchet group: the most files Sudsy's safety check refuses (an internal error, not a syntax error)
  prettier-tests: 0
intentional:            # only the lead or the user adds these: name -> invalid-input | tool-wrong
  subst-indent: tool-wrong
fixes:                  # gap name or lint rule -> one line: where and what to change (a name no longer in `differences` or `missed` fails the run)
  for-no-in: crates/lang-bash/grammar, accept `for x do`
missed:                 # lint: rule -> findings of the corpus it misses (the 15 largest; `scripts/parity.sh coverage <tool>` checks it, `COVERAGE_WRITE=1` writes it)
  SC2086: 28
unclassified: 12        # format: most differing files of the ratchet groups that no `name:N` explains (a ratchet)
pins:                   # file -> pin of Sudsy's output for it, for the tool-wrong names (scripts/parity.sh --pin <tool> prints them)
  corpus/bats-core/contrib/release.sh: 3fa9c01d7e5b2a64
```
`choice` is intentional and documented (the `choice` names are the generated block `<!-- generated:differences:<tool> -->` of the language's `docs/ai/formatting` page, written by `cargo xtask codegen`); `gap` is unintended, to fix, and stays out of the user docs. A text with `: ` or ` #` in it is quoted. The run fails on a differing file that is not listed (outside the ratchet groups), a listed file that no longer differs (stale), a name no file uses, a name that is not defined, and a ratchet group below its minimum; above it, the run prints the count to raise the minimum to. Format runs also format Sudsy's own output once more (Prettier is not involved: Sudsy must reach a fixed point on its own output) and count the files that change, per ratchet group (`fixtures` for the ungrouped ones); the run fails above the `second-format` maximum and prints the count to lower it to. A file the safety check refuses is not formatted, so it is in no second-format count: the `refused` maximum counts those files the same way (a bug that the guard caught; the target is 0). The target is 0 for every group, and no input is dropped to lower it. `PARITY_FILTER` lists the files that change. The report ends with the number of files per name, `choice` then `gap`, and the ratchet lines.

Every run (format, lint, coverage) prints two numbers, defined in [../design/parity-target.md](../design/parity-target.md): **raw** (the share measured as before) and **target** (the share a user of the tool can get from Sudsy; 100% means all of it), then the intentional groups with their counts and the count of every input filter (`skip`, `skip_with`, non-UTF-8 files, files the tool rejects or cannot read, findings left out). The target leaves out only the reviewed intentional cases; everything else counts against Sudsy. The `intentional` map gives a name one of two values: `invalid-input` (the file is excluded from the target; the tool rejecting it is the evidence) and `tool-wrong` (the tool's output changes meaning, drops content or is unstable). A `tool-wrong` file is pinned: `pins` holds the first 16 hex digits of the SHA-256 of Sudsy's output for it, so a later change to that output is printed as `REVIEW` and counts against Sudsy until the lead reviews it and pastes the new pin from `scripts/parity.sh --pin <tool>` (a format run that also prints the pins of the `tool-wrong` entries; the runner never writes them). A lint finding is pinned by its key (file, rule, line), so no hash is needed; a finding that moves is unlisted and counts. In a coverage run the target leaves out the findings of `wontfix` catalog entries and counts the findings of `formatter` ids, which the raw share leaves out, as missing until the tool has a proof run. Every coverage run of a tool with `formatter` catalog entries is that run, not an option: it copies the corpus, formats the copy with `sudsy format` under the tool's preset, runs the tool again and prints the findings of `formatter` ids that remain; only those count as missing in the target. A file `sudsy format` rejects stays unformatted, so its findings remain. Two more keys of `differences.yaml` serve the target. A file the tool rejects is always `invalid-input`, with no entry needed: the target leaves it out, the raw share keeps it, and every run prints the group with its count (a ratchet group also counts them as `rejected by <tool>`). When Sudsy rejects a file and the entry is `invalid-input`, the language's reference parser must reject it too: a format entry with `reference_parser` (`npm`, `version`, `script`: a Node script that exits 1 on a syntax error; Prettier's GraphQL files use graphql-js 16) is run on those files, and one it accepts is printed as a Sudsy bug and counts as `REVIEW`. `flags` names each reference-tool flag that turns a feature off (`--no-config`, `--skip-javadoc-formatting`, `ignore_trailing_blanks`, `skip_with`) with its reason; every run prints `flag <name> (gap): N fixtures` for it, N being the fixtures the flag applies to (the files it changed the result of, for `ignore_trailing_blanks`; the files skipped, for `skip_with`). In a lint coverage run the raw share and the target both need the same line (the column is not compared; every `parse` of `scripts/parity_tools.json` has a `line`): a report on another line is missing. The target also leaves out a finding that is a reviewed `tool-wrong` one, listed in `differences.yaml` as `<file> <tool>:<rule> <line>` under an `intentional` name. `scripts/parity.sh --test` runs the runner's tests (`scripts/test_parity.py`: a pinned file whose output changed, the filter counts, the `fix` command), part of the gate.

## The queue
`docs/ai/parity/queue.md` (generated by `cargo xtask codegen` from every `differences.yaml`, kept current by `codegen --check`) lists per tool the open work: the unclassified count with its share of the differing files, the `gap` names ranked by files, and for lint the rules ranked by missed findings, each with its `fixes:` note. In `files`, a ratchet group's names may end in `:N` (`real-world: scss-layout:300, comments`): N differing files have that name as their first cause, so classifying a group's files is writing those numbers; the files of a ratchet group without `:N` stay unclassified, and the run prints `unclassified: N of D` and fails when N rises above `unclassified:` (a ratchet: lower it when the run says so); a tool without the key only prints the count (set it). A gap that reaches 0 files is removed with its `fixes:` note (the run reports an unused name). A parity step reads the tool's section first, classifies before it fixes, keeps unclassified under 15% of the differing files, takes the items from the top and commits the regenerated queue with each landing.

## eslint-jsonc
`scripts/parity.sh eslint-jsonc` uses ESLint 9 with eslint-plugin-jsonc (`docs/ai/parity/eslint-plugin-jsonc.yaml`; needs Node), copies `tests/parity/eslint-jsonc/` to `work/` there so that `eslint.config.mjs` finds the plugin, and runs ESLint on every `.json` fixture. A fixture's name selects the rule and options: `eslint.config.mjs` enables one rule per fixture and `sudsy.yaml` enables the matching Sudsy rule through `overrides`, so both sides stay in step. `sorted-keys` and `sorted-array-values` report the entries that would have to move; where several shortest edits exist ESLint's pick can differ from Sudsy's, so fixtures stick to cases both agree on (the catalog `gap` says so).

## markdownlint
`scripts/parity.sh markdownlint` uses markdownlint-cli2 (needs Node), copies `tests/parity/markdownlint/` (the `.md` fixtures and a `.markdownlint.jsonc` that turns on only the rules Sudsy has an equivalent for) below its install folder and compares `(rule, line)` of every fixture: markdownlint reports a column for some rules only, so columns are not compared. The Sudsy rule of a `rule:` status stands for the MD id of the catalog entry.

## hadolint
`scripts/parity.sh hadolint` runs hadolint with `-f json` and `sudsy lint` (config: `tests/parity/hadolint/sudsy.yaml`, `preset:dockerfile/hadolint`) on the rule fixtures of the Dockerfile rules, `tests/rules/dockerfile/*/*.dockerfile` with their annotation lines removed, so the fixtures are not copied. `(rule, line)` is compared for the rules the catalog maps; hadolint's other codes (deferred DL rules, ShellCheck) are ignored. The rule fixtures are written to agree with hadolint; a case where it deliberately differs goes into its [differences](#differences-lists) (the lint key form).

## shellcheck
`scripts/parity.sh shellcheck` is the hadolint mode for shellcheck, run with `-s bash -o all -f json` (the optional checks are in the catalog, so they are on) and compared as `(rule, line)` with `sudsy lint` under `tests/parity/shellcheck/sudsy.yaml` (`preset:shell/shellcheck`) on `tests/rules/shell/*/*.sh` without annotations.

## checkmake
`scripts/parity.sh checkmake` is the hadolint mode for checkmake, run with a JSON line template on `tests/rules/makefile/*/*.mk` without annotations; `sudsy lint` runs under `tests/parity/checkmake/sudsy.yaml` (`preset:makefile/checkmake`). checkmake runs all its rules on every file, so a fixture is compared on the rule of its own folder only (`(rule, line)`), and the two rules checkmake reports a line late (`timestampexpanded`, and `minphony` at the `.PHONY` line, which it reads as a variable) are moved back. Fixtures with a `<name>.rules.yaml` set rule options and are left out.

## ruff
`scripts/parity.sh ruff` is the lint mode for ruff: `ruff check --isolated --ignore-noqa --target-version py314 --select <the catalog's mapped codes> --output-format json` once on the rule fixtures (`tests/rules/python/*/*.py`, annotations removed) and the real-world projects of the format parity (`tests/conformance/fetch-python-corpus.sh`, fetched by the run; without the corpus only the rule fixtures are compared, about 120 findings against 445 with it), and `sudsy lint` (`tests/parity/ruff/sudsy.yaml`, `preset:python/ruff`) on each file, compared as `(rule, line)`. The lint entry's `command` and `env` (`python -m ruff check ...`, `PYTHONPATH={prefix}`) serve the fixtures and the coverage run alike. `scripts/parity.sh format ruff` is the format mode (below).

## actionlint
`scripts/parity.sh actionlint` is the hadolint mode for actionlint, with the pinned corpus (`tests/conformance/fetch-github-actions-corpus.sh`: actionlint's own `testdata/ok`, `err` and `examples`, and the starter workflows). Each rule fixture (`tests/rules/github-actions/*/*.yml`, annotations removed) and each corpus file is copied to `.github/workflows/` of a work folder (a workflow is claimed by its folder), run through `actionlint -format '{{json .}}'` with the shellcheck and pyflakes integrations off, and through `sudsy lint`. An actionlint error becomes a catalog id from its `kind` and message (`actionlint_check` in `scripts/parity_lint.py`: `job-needs/cycle`, `expression/untrusted`, ...); the ids the catalog maps to a rule are compared as `(rule, line)`, the others are left out.

## psscriptanalyzer
`scripts/parity.sh psscriptanalyzer` uses the PSScriptAnalyzer module of invoke-formatter (needs `pwsh`) and runs `Invoke-ScriptAnalyzer` (`scripts/parity_psscriptanalyzer.ps1`) with the catalog's `rule:` entries that the preset `powershell/psscriptanalyzer` turns on, on the PowerShell rule fixtures (`tests/rules/powershell/*/*.ps1`, annotations removed) and the corpus (`tests/conformance/fetch-powershell-corpus.sh`), compared with `sudsy lint` (`tests/parity/psscriptanalyzer/sudsy.yaml`, that preset) as `(file, rule, line)`. It also checks that the catalog lists exactly the rules of `Get-ScriptAnalyzerRule`. A lint key is `corpus/<path> <psscriptanalyzer|sudsy>:<rule> <line>` (a fixture is `<folder>-<name>.ps1`).
## stylecop
`scripts/parity.sh stylecop` copies `tests/parity/stylecop/` (a net10.0 project referencing StyleCop.Analyzers at the catalog's version, plus `.cs` fixtures) to `target/parity/stylecop-plain/` and `stylecop-fixed/`, enables every catalog SA id of status `rule:` or `formatter`, or `option: csharp.format.<name>` for an option the `csharp/stylecop` preset sets, as a warning through a generated `.editorconfig`, and runs `dotnet build` with an SARIF error log. Two comparisons:
- plain: each `rule:` SA id, mapped through the catalog, must be reported by `sudsy lint` at the same `(rule, line, column)`, and `sudsy lint` must report nothing else of the mapped rules;
- fixed: after `sudsy fix --unsafe .`, StyleCop must report none of those formatter ids whose coverage is `covered` (in any fixture) or `partial` (in the `layout_*` fixtures; the older fixtures show their gap), and what it still reports for `rule:` ids must match `sudsy lint`.
The fixtures' `sudsy.yaml` extends `preset:csharp/stylecop`, so the formatter ids are checked under the preset's options and the `rule:` ids with the rules the preset enables. The `layout_*` fixtures are the layout rules' violations; the `doc_*` fixtures (summary, tags, wording, text) are the SA16xx documentation rules' cases, valid C# in which every partial type has only parts that StyleCop and Sudsy judge alike (StyleCop accepts one documented part, Sudsy checks each); the run prints the formatter ids no fixture violates (the build would pass vacuously for them). Needs the .NET SDK and network for the NuGet restore. To add a case, add a `.cs` file and enable its Sudsy rules in the preset (`crates/lang-csharp/presets/stylecop.yaml`); the catalog drives the id mapping.

## Nightly
`.github/workflows/nightly.yml` (daily 02:17 UTC, and `workflow_dispatch`) runs every parity tool of `scripts/parity_tools.json` and every language crate with ignored conformance tests, so a broken ratchet (`ratchet` minima, `second-format` and `refused` maxima, a new mismatch) or a broken corpus test fails without a person. `scripts/ci-nightly-matrix.py` builds the job matrix: one job per tool (`scripts/parity.sh [format] <tool>`) and per crate (`scripts/conformance.sh lang-<x>`: the fetch script, then `cargo test --profile corpus -p lang-<x> -- --ignored` minus the measurements `measure_startup_cost`, `scaling` and `model_cost`; `#[ignore]` reasons with "measurement", "prints timings" or "flaky" do not select a crate). A new tool or crate joins by existing; nothing is listed twice. Jobs do not stop each other and carry the tool's or crate's name. Tools (`target/parity`, keyed on the pins in `parity_tools.json`, `docs/ai/parity/*.yaml`, `jre.sh`, `dotnet-tools.json`) and corpora (`tests/conformance/corpus`, keyed on the fetch scripts, which update a stale cache by commit) are cached per job; the Cargo cache is saved from the default branch only. A cache is saved only by a passing job.

## Rule inventory
`scripts/parity_inventory.py <tool>|--all [--write]` compares a lint catalog with the rules of the tool's pinned version (the catalog's `version`): an npm plugin loaded by Node (ESLint and its plugins, stylelint and its plugins, html-validate, htmlhint, markdownlint), `ruff rule --all` from the PyPI wheel, the files of a wheel (yamllint, sqlfluff) or a raw file at the tool's tag (Roslynator's `Analyzers.xml`, tflint's and hadolint's rule lists). It prints the counts and the catalog ids the tool lacks, and with `--write` appends the missing rules to `entries:` as `planned` (deprecated: `wontfix`, ruff preview: `deferred`); `cargo xtask codegen` then regenerates the counts. Sources are the `SOURCES` table of the script; a tool without one (shellcheck, checkstyle, ktlint, StyleCop, actionlint, buf, PSScriptAnalyzer and the formatters) is listed by hand or by its own parity run. It needs Node and network.

## Coverage mode
`scripts/parity.sh coverage <tool>` measures what a team that switches would lose: the tool's default or recommended set runs on its real-world corpus and the result is the share of its findings that the mapped Sudsy rule also reports on the same line of the same file (`parity_lint.py <tool> ... --coverage`). A finding counts as covered when `sudsy lint` with the preset that mirrors the tool's default set (the tool entry's `preset` in `scripts/parity_tools.json`: `python/ruff`, `js/eslint-recommended`, `yaml/yamllint`, ...; a pure config file that lists the mapped rules of that set) reports the Sudsy rule the catalog maps its rule to on that line of that file and, when the upstream message quotes a name (`` `os` ``, `'x'`) and the Sudsy rule's messages do too, a message with the same name; the column is not compared. A rule with no mapping is uncovered. The report lists the rules with most uncovered findings (a mapped rule with 0 covered misses it or is not in the preset; one marked `no Sudsy rule` is unmapped) and ends with the preset share, the headline and the usability bar (at least 85%), and, for information only, the share with Sudsy's default config (no `sudsy.yaml`: what a user gets on first run, bug-only rules) and with every mapped rule on; the run fails when the preset share is below `coverage:` in the tool's `differences.yaml` (a ratchet, only raised: the run says when to) and `cargo xtask codegen` copies the number into the table of [../parity/README.md](../parity/README.md). Fixture runs (`scripts/parity.sh <tool>`) compare `(rule, line)`.

| sqlfluff | the default rules (layout and capitalisation included) on the SQL corpus (1,122 files), each in the dialect of its folder (`ansi`, `postgres`, `mysql`, `tsql`) |
| buf | `STANDARD` on the Protobuf corpus, one workspace per project of it (googleapis, its preview, protobuf, grpc); a file buf cannot compile (an import the corpus lacks, an edition buf does not know) is left out and counted |
| tflint | `--recursive` with the Terraform ruleset built into tflint 0.66.0 (its defaults) on the HCL corpus; the catalog pins the ruleset's own version, so tflint's is the entry's `version`; a module tflint cannot load gives no findings |
| actionlint | its checks without the ShellCheck and pyflakes integrations (Sudsy's Shell language does those) on the GitHub Actions corpus, copied into `.github/workflows/`, which is how a file is found as a workflow; most of the corpus is actionlint's own test inputs |
| checkmake | the default rules on the Makefiles of the Makefile corpus (59) |
| ktlint | the `ktlint_official` code style on the Kotlin corpus without the compiler's sources |
| checkstyle | `google_checks.xml` (the rules by their check names: the `Google` prefix of an id is dropped) on the Java corpus (5,337 files) |
| psscriptanalyzer | the default rules on the PowerShell corpus (210 files); needs `pwsh` on the path |
| phpstan | level 0 on each project of the PHP corpus (10,390 files, no `vendor/`: a class of a dependency is unknown, so `class.notFound` is most of its findings); needs `php` 8.1 or later on the path |

The gap is real, not a measuring fault: a rule that has a Sudsy mapping and is in the preset is covered at 100% of its findings; what is missed are rules with no Sudsy rule yet. ruff 0.17's default set (no config, `--isolated`) is 407 rules, far more than the E4, E7, E9 and F of older versions (`ruff check --isolated --show-settings`); `python/ruff` is generated from that list and the catalog. The run prints the top 15 missed rules.

`scripts/parity.sh coverage rubocop` compares by rule and line (`Lint/X` at line N against the mapped rule at line N), the default config with `--only Lint` (the preset is `ruby/rubocop`) and Ruby 3.4 on a copy of the Ruby corpus of `tests/conformance/fetch-ruby-corpus.sh`; RuboCop is a gem (`"install": {"gem": ..., "ruby": ...}` in `scripts/parity_tools.json`: the system Ruby, else the ruby-builder tarball of that version, below `<target>/parity/`). The report ends with what only Sudsy finds per rule. There are no fixture runs for it: the rule fixtures are `tests/rules/ruby/rubocop-lint`.

The preset of a tool is pure config data: the rules of the tool's default set that the catalog maps, at `warn` with their default options (a generated list; `python/ruff` from ruff's own `--show-settings`, the Vue, Svelte and html-eslint presets from the plugin's recommended config; stylelint's is `css/stylelint-standard`, the config the run uses). The all-rules number turns on every rule the catalog maps on top of the preset, so the gap to the preset number is what the default-set filter of the preset holds back. Findings of a rule with `formatter` status in the catalog are left out (the formatter owns them) and counted on the first line of the run; a file the tool cannot read at all is left out too (`unreadable`) and counted. A tool that does not finish on a file (time or memory) leaves it out, listed in the run.

Not measured: `clang-tidy` (no catalog, and Sudsy has no C or C++ lint rules), detekt, PMD, PHPCS (not catalogued), `eslint-plugin-jsonc` (the JSON corpus is a parser test suite, no real-world files), `stylelint-scss` and `stylelint-less` (plugin rules without a recommended set of their own), `angular-eslint`, `graphql-eslint`, `biome`, `taplo`, `terraform` (no entry has a corpus run yet), and the C# analyzers: the compiler skips analyzers when the compilation has errors, and the C# corpus (the .NET runtime's CoreLib sources) does not compile on its own (118,604 compiler errors), so StyleCop reports nothing on it; a run needs a compiling corpus project or an analyzer driver that tolerates errors.

## Tool entries
A tool is an entry of `scripts/parity_tools.json`, under `lint` or `format` (`parity_format.prepare` serves both modes), so installing one is config only (plus its `tests/parity/<tool>/` folder with `sudsy.yaml` and its `docs/ai/parity/<name>.yaml` with the pinned `version`):
- `catalog`: the catalog file whose `version` pins the tool (`version_command` instead: the SDK's own, for `dotnet-format`); `install`: an `npm` package (`with`: more packages), a `pip` package, a `dotnet-tool`, a `psmodule`, a `jar` (a Maven Central jar with its `sha256`, run with the pinned Temurin JRE that `scripts/lib/jre.sh <dir>` installs next to it, checksum verified; the runner writes a launcher script as the `exe`) or a `release` (URL template, per-platform `assets`: a zip or tar archive, a gzip or the executable itself) and its `exe`, installed into `<target>/parity/<catalog>-<version>/` on first use (a lint entry may name a format entry whose install it shares: `"install": "buf"`);
- `version`: the tool's release when the catalog pins something else (tflint: the ruleset's version);
- `needs`: `worker` builds the C# worker; `fetch`: scripts that fetch corpora;
- `coverage`: the entry of the coverage mode, run by `scripts/parity_coverage.py` for every tool without code of its own in `parity_lint.coverage`: `corpus` (`dir`, `glob`, `skip`; `as` or `into` name where the files go in the work folder), `command` (`{exe}`, `{prefix}`, `{python}`, `{work}`, `{root}`, `{group}`, `{files}`; without `{files}` it runs once per group), `group` (a regex whose first group splits the files into runs, `cwd: group` runs one in the folder of its name), `chunk`, `timeout`, `memory_gb`, `ok_codes`, `env`, `stream` (`stderr` where the report is there), `files` (config files written into the work folder), `parse` (`format` `regex` with named groups `file`, `rule`, `message`; or `json`/`jsonl` with `levels`, the lists to walk, and `file`, `rule`, `message` as `<level>.<key>.<key>`; `rule_prefix`, `rule_sub`, `rule_fn`, `json_line`), `map_also` (catalogs whose mapping also applies: hadolint runs ShellCheck), `instruction` (`rule_prefix`, `continuation`: findings whose code starts with the prefix count as covered when Sudsy reports the same rule on any line of the instruction that starts at the tool's line, an instruction going on while a line ends with `continuation`; hadolint reports ShellCheck codes at the first line of a `RUN`, ShellCheck at the line of the command), `unreadable` (rules that mean the tool could not read the file) and `sudsy` (`extends`, or `mapped_rules: <language>`). The tool reports into files, not pipes: a Node tool that exits after a write cuts a pipe at 64 KiB.

## Speed
`scripts/speed.sh [<tool>...]` ([plan](../design/speed-comparison.md)) measures the entries that have a `speed` key (one object, or a list: one per language), run by `.github/workflows/speed.yml`; a tool with no parity run (oxlint, dprint, `biome-js`) is an entry of the `speed` section, with no `command` and no `coverage`. A tool with a format and a lint entry carries the key on the format entry. The key:
- `language` and `label`: the README table.
- `corpus`: a name of the `corpora` section (`text`, `copies`, `fetch`, `sources` as fixtures); `{"group": <ratchet group of the entry's fixtures>, "text": ...}` (`fixtures` is the ungrouped ones); or `{"coverage": true, "text": ...}`, the corpus of the lint entry's coverage run.
- `format` and `lint`: the tool's check commands, run in the corpus copy (`c/` below the work folder, with Sudsy's `sudsy.yaml` above it). Placeholders: `{prefix}`, `{exe}`, `{python}`, `{root}`; an argument `{files}` is every corpus file, 500 per process. `"lint": "coverage"` runs the coverage command of the lint entry (its `files` and `env` too) on the same files.
- `preset` (format; a name or a list) and `lint_preset`: the Sudsy side's mirroring preset. Without them the format run uses `tests/parity/<sudsy or the tool>/sudsy.yaml` and the lint run the preset of the tool's lint entry; with none, the row is `not measured: no mirroring preset`.
- `not_measured`: `{"<task>": "<reason>"}`, a task that cannot run here (no install, no run, no row of numbers). A tool whose setup or run fails gets the same row with the error.
- A Sudsy run that crashes, exits above 1 or reports `0 file(s) checked` fails its row (`not measured: run failed`): a time without files is a wrong folder or preset, not a result.
- `env` (`{prefix}`) and `files` (config files written into `{prefix}`).

Example: `"speed": {"language": "Python", "label": "ruff", "corpus": {"group": "real-world", "text": "the Python corpus"}, "format": ["{python}", "-m", "ruff", "format", "--check", "--isolated", "--no-cache", "."], "lint": ["{python}", "-m", "ruff", "check", "--isolated", "--no-cache", "."]}`. A Sudsy run that exits with an error stops the tool's row. Output: `bench/speed.json`; `cargo xtask codegen` writes the README table from it.

## Format mode
One runner (`scripts/parity_format.py`) serves every format tool; an entry also has:
- `command`: the tool's command line with `{prefix}`, `{exe}`, `{python}`, `{root}`, `{group}` and `{file}` (a Python tool runs as `{python} -m <tool>` with `env` `PYTHONPATH={prefix}`; there are no wrapper scripts, only the PowerShell tools have one: no `pwsh` command line exists); `env`: variables of the run (`{prefix}`); `group`: a regex over the fixture's name whose first group is `{group}`; `input`: `arg` (the file name is an argument), `stdin`, `in-place` (the tool rewrites a copy) or `batch` (one run over copies of all fixtures, for a tool that starts slowly; `reject`: a regex over the tool's output whose first group names a file the tool rejects); `tool_may_reject`: a file the tool rejects is a difference, not an error;
- `fixtures`: sources of fixtures, each a `dir` (default: the tool's folder) with `suffixes`, a fixture-name `prefix`, `recursive`, or a `list` file with `starts`; `kind: editorconfig-cases` is the `dotnet-format` layout below.

`scripts/parity.sh format prettier|biome` formats every JSON and YAML fixture in `tests/parity/<tool>/` with the tool (`prettier --no-config --no-editorconfig --embedded-language-formatting=off`, `biome format` with its defaults) and with `sudsy format`, and compares the outputs byte for byte. The tool is installed with npm at the catalog's `version` into `target/parity/<tool>-<version>/` on first use (needs Node and network); the fixtures are copied to `target/parity/<tool>-work/` first because `sudsy format` writes in place. The folder's `sudsy.yaml` extends the matching presets (`json/prettier-compat` and `yaml/prettier-compat`; `json/biome`), so a difference is a preset or formatter gap. Every difference is printed as a unified diff and the exit code is 1.

The `prettier` fixtures also include GraphQL: the folder's `.graphql` files and the corpus of `tests/conformance/fetch-graphql-corpus.sh` (`graphql/<repo>/<path>` in `differences.yaml`; Prettier's own tests in it include files it rejects, which count as differences unless listed, `tool_may_reject`). The `prettier` fixtures also include the folder's `.md` files, the repo's `docs/**/*.md` and the dotnet/runtime coding-guidelines docs (`tests/conformance/fetch-markdown-corpus.sh`, pinned); Prettier runs with `--embedded-language-formatting=off`, and the folder's `sudsy.yaml` sets `embedded_language_formatting: off`, because Sudsy's formatters of the fenced languages make other choices than Prettier's.

Fixtures that differ are listed in the folder's `differences.yaml` ([below](#differences-lists)). Fixtures named `crlf.*` keep CRLF line endings (`.gitattributes`: `-text`).

## eslint

`scripts/parity.sh format ktlint` installs the ktlint CLI jar at the catalog's `version` (`docs/ai/parity/ktlint.yaml`, `jar` install into `<target>/parity/ktlint-<version>/`, with a pinned Temurin JRE; needs network) and formats every `.kt` and `.kts` of the Kotlin corpus (`tests/conformance/fetch-kotlin-corpus.sh`, without the compiler's own sources) in one `ktlint --format` run (`input: batch`; the `ktlint_official` code style, the tool's defaults) against `sudsy format` under the folder's `sudsy.yaml`. A file ktlint cannot parse is rejected. The ratchet group is `real-world`; the run takes about 9 minutes.

`scripts/parity.sh format php-cs-fixer` installs the PHP-CS-Fixer phar at the catalog's `version` next to a static PHP build (`release` install with an extra `files` entry; `<target>/parity/php-cs-fixer-<version>/`; needs network) and formats every `.php` of the PHP corpus in runs of 200 files (`input: batch`, `chunk: 200`, config `tests/parity/php-cs-fixer/per-cs.config`: `@PER-CS`, no cache). A failed run is repeated file by file and a file PHP-CS-Fixer rejects is not counted. The ratchet group is `real-world`; the run takes about 15 minutes.

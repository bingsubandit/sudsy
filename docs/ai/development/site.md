# Documentation site

Public rule reference at https://bingsubandit.github.io/sudsy/, built with Astro Starlight (versions pinned in `site/package.json`; latest version only). Everything outside `getting-started.mdx`, the landing page (`index.mdx`) and the two index pages is generated; the rest of `docs/` is for contributors and is not published.

## Build and preview
`scripts/site.sh build` (`npm ci`, generate, `astro build` into `site/dist`), `scripts/site.sh dev` for the dev server (no search index there; the rules index says so), `scripts/site.sh preview` to build and serve the site with search at http://localhost:4321/sudsy/. `scripts/site.sh test` first checks that `site/src/data/sessions.json` equals a fresh run of the CLI (needs the debug CLI of the build slot or `SUDSY_BIN`; `scripts/site.sh sessions` rewrites it), then builds, serves `site/dist` with `astro preview` (port 4399, `SITE_PORT` overrides; `SITE_NO_SERVER=1` tests a server that is already running, since `astro preview` is one daemon per host) and runs `site/test/smoke.mjs` (Playwright against the installed Edge or Chrome; no browser download): the full rule table, search, every filter menu with chips and Clear, keyboard use of the menus, query-parameter preselection, the single Rules sidebar entry, rule pages (badges, short and long configuration, upstream links and the Match column, the capped example, squiggles), an upstream-id redirect, tool pages (a tool with a measured lint or format share never says it was not measured; the index shows a formatter's share per language), language pages (only their own presets), the landing page (sections, numbers equal the data, the speed claim of the Speed section computed and linked to `/speed/`, which lists every row and marks the slower ones, install tabs by click and keyboard, terminal tabs, the README's CI step, the language grid with the twelve most popular languages and a link to all (a phone shows the first eight), speed cards, no JavaScript, reduced motion, 360 px, axe WCAG A and AA in light and dark on the landing page, Getting started, Compared tools and a language page, weight under 500 KB), progress bars (fill equals the number, the tick, the not-measured state, labels, every language present), no horizontal overflow at 1200 and 360 px, the landing tagline, the header search, and no console or network errors. `scripts/site.sh check-links [tool...]` checks every upstream rule URL (network, nightly); `scripts/site.sh list-bench [PORT]` serves the build and prints page weight and the time of the first filter, `scripts/site.sh landing-bench [PORT]` the weight and largest contentful paint of the landing page ([performance/numbers.md](../performance/numbers.md)). `astro preview` runs as a daemon (`astro preview stop`). Node 24. `scripts/site.sh scale-test [N]` builds with N synthetic rules (default 10 000) from a copy of `rules.json` in the build slot and prints build time and sizes ([performance/numbers.md](../performance/numbers.md)). The site is not part of `scripts/gate.sh`; the `site` workflow builds it.

## Data
`site/scripts/generate.mjs` writes Markdown into `site/src/content/docs/generated/` (git-ignored) before each build:
- `docs/ai/rules/rules.json` (from `cargo xtask codegen`; `SUDSY_RULES_JSON` overrides the path): one page per rule at `/rules/<id>/` laid out as a header block of badges (languages as links, category, fix kind, default level), "What it does", "Why it matters" (when the rule has a `why`; both texts keep their paragraphs), the example (the fixture input with the reported spans as red wavy underlines whose hover text is the rule id, then the fixed output; an input over 25 lines is cut to the lines around the spans, with less context and then fewer spans until at most 30 lines remain), one Configuration section and the upstream table last. A rule without options shows the short form `rule-id: warn  # off (default), warn, error`; a rule with options shows `rule-id:` with `level` and its options at their defaults, the options table (Option, Type, Default, Description; allowed values sit under the description), the presets that enable it and the suppression comment. The upstream table has the tool, the id as a link to the upstream rule's own page (the `rule-url` of the parity catalog; a tool without per-rule pages links its home page) and `Match`: `full`, or `partial`; the "What differs" column with the catalog's gap note exists only when a row is partial; a rule of several languages has one page. The underlines are the `squiggles="line:column:length,..." tip="..."` meta of a code block, handled by the small Expressive Code plugin in `site/ec.config.mjs`.
- Each upstream id (`SA1005`, `DL3008`) gets `/rules/<id>/` too, as a plain static file in `public/rules/` (git-ignored; a Starlight page would carry 19 KB of layout): a meta refresh and canonical link to the Sudsy rule when one rule matches, a list of links when several do. Not in the search index; rule pages list their upstream ids. Ids with characters outside `A-Za-z0-9_-` are slugified; an id equal to a Sudsy rule id is skipped.
- `docs/ai/parity/site.json` (from `cargo xtask codegen`: the rows of `xtask/full/support.yaml` with their measured shares, speed rows and presets, and every parity catalog with its coverage) via `site/scripts/pages.mjs`: one page per language at `/languages/<id>/` (parity bars, speed, presets, rule count), one page per compared tool at `/compare/<tool>/` listing every rule and setting of the tool with the Sudsy rule, the status and the gap note (a rule's id links to the upstream rule's page; the columns have fixed widths and a rule id breaks at `-`), and the two indexes `/languages/` (one card per language with its status badge and a Format and a Lint group of bars, and a count of ready and in-progress languages) and `/compare/`. A measured share is a progress bar from `site/scripts/bars.mjs`, plain HTML and CSS with no script: filled to the floored percent the README shows, a tick at 85, green from 85 and orange below, a dashed empty track with the words "not measured", and an `aria-label` such as "Format: 95% of files identical to Prettier" on the track; the first tool of a group is drawn larger. A group without a reference tool shows its text. The component is written once for reuse (the landing page's language grid). Rule pages link their languages and upstream tools.
- `crates/lang-*/presets/*.yaml` with the notes column of `docs/ai/formatting/presets.md`: `/reference/presets/`.
- `schemas/sudsy.schema.json`: `/reference/format-options/`.
- A language page lists the presets of its own: the folder of the preset is one of the row's language ids or the crate of one of its languages (`discover.rs`, `own_preset`), so Vue, Svelte and Angular templates list the `html/` presets, and PHP does not list `js/oxlint` because that preset enables a shared rule PHP also has.
- A compared tool's measured shares: its lint share (the parity target) and the format share of each language that names it as a reference formatter. The tool page shows one badge per share, the index one bar per share (`Lint`, then one `Format` bar per language); `not measured` stays only for a tool with neither (`angular-eslint`, `dotnet-format-editorconfig`).

## Landing page
`src/content/docs/index.mdx` (splash template) is the seven sections of [design/landing-page.md](../design/landing-page.md), one component each in `src/components/landing/`; the styles are `src/styles/landing.css` (the pink of the logo and the blue of the site, always-dark terminal, no external fonts or scripts; a `js` class set by an inline head script shows what needs JavaScript, so without it the first install and terminal panel show). Every number and text is read at build time by `scripts/landing.mjs` from `site.json`, `rules.json` or the README (ready and in-progress counts, preset, rule and safe-fix counts, the early-release note, the README's before / after CI step); the speed cards are the Format and Lint rows of the primary reference tool (first of each column) of the first five languages of the support table that have a measured row, slower results of Sudsy included, bars scaled to the slower of the two. The install commands are `scripts/install.mjs`, used by `InstallTabs.astro` (landing page twice, Getting started once) and the Markdown twin. The terminal is `src/data/sessions.json`: `scripts/sessions.mjs` runs `sudsy check`, `fix` and `format` (then `git diff`) on copies of `site/demo/` (the same `sudsy.yaml` the page shows) and writes the output as printed; `--check` is the freshness test. Components read data through paths relative to the working directory (`site/`), since a bundled component has no repository-relative `import.meta.url`.

## Agent docs
`site/scripts/agents.mjs`, called by `generate.mjs`, writes into `public/` (git-ignored): a Markdown twin of every page (`/<slug>.md`, from the same front matter and body, with layout HTML and the editor meta removed and links pointing at twins; the landing page and the rules index, which are a hero and a component, get a short text), `llms.txt` (guide, machine-readable outputs, every language and compared tool page as a link, per the llms.txt convention), `llms-full.txt` (the guide and language pages in one file; rule and tool pages stay out, they are fetched one at a time) and `rules.json` (a copy of `docs/ai/rules/rules.json`). The hand-written `cli.md` documents the commands, the `--format json` shape, `rules.json` and `init --agents`; there is no `rules --json` command, the file is the machine-readable rule list.

## Search engines
Every page carries a canonical URL (Starlight, from `site`/`base` in `config.mjs`), `sitemap-index.xml` (Starlight's sitemap integration; `robots.txt` points to it), and the OpenGraph and Twitter image `og.png` (`assets/logo/og.png`, the logo on a 1200x630 background; copied to `public/` by the generator). `public/google016a7f3076a694ed.html` is the committed Google Search Console verification file; keep it. The `<title>` of rule, language and tool pages is set per page through `head` in the front matter: a rule names its languages and the tools it matches (`no-debugger: JavaScript / TypeScript lint rule, like ESLint no-debugger | Sudsy`), a language names its reference tools, a tool page names the tool. Descriptions are generated too.

## Page check
`generate.mjs` fails the build (and so the `site` workflow) when a rule has no page, a language of a rule has no row in `support.yaml`, or a language row or compared tool has no page. `cargo xtask codegen` fails when a language of the providers or a language name of `bench/speed.json` is in no row of `support.yaml`, since that language would have no page.

Hand-written: `src/content/docs/` (landing, getting started, rules index), `src/components/RuleSearch.astro`, `astro.config.mjs`.

## Search
Starlight's built-in Pagefind search covers every page (header search). The rules index (`/rules/`, `RuleSearch.astro`) does not use Pagefind: `generate.mjs` writes `public/rules-index.json` (one record per rule: id, languages, category, fix, presets, upstream ids and tools with their URLs, description), the page fetches it once and renders every rule as a table row in chunks (no 50-hit cap, no per-rule request; on narrow screens a row is a card). A search box matches id, description and upstream ids. Filters are one menu per filter (`language`, `category`, `fix` (`none`, `safe`, `suggestion`, `unsafe`), `preset`, `upstream` tool) with the count of each value under the other active filters, a find field in the long menus, chips for the active values with a remove button (above the menus, so an open menu never covers them), and a Clear button; on narrow screens the menus collapse behind one Filters button. Several values of one filter match any. Menus open and close with Enter and Escape and use native checkboxes. `?language=csharp`, `?preset=...`, `?q=...` and the other filter names preselect and are kept in the address. A rule for `all` languages matches every language filter. The sidebar lists no rules (Starlight renders it into every page, so it would grow with the square of the rule count); it has one "Rules" entry, the index. The default level is not a filter: levels are configurable.

Styles are plain CSS on Starlight's tokens in `site/src/styles/site.css` (badges, rule header, tables, list); light and dark follow the theme.

## Deploy
`.github/workflows/site.yml` builds the site and uploads the Pages artifact. It runs on pull requests and pushes to main that touch the site inputs (`site/**`, `docs/ai/rules/rules.json`, `docs/ai/parity/site.json`, `assets/logo/og.png`, `docs/ai/formatting/presets.md`, the schema, preset files) and fails when `site/dist` exceeds 800 MB (the Pages limit is 1 GB); a push to main also deploys (Settings > Pages > Source is "GitHub Actions"). The VS Code extension's `DOCS_BASE_URL` and diagnostic links switch on after the site is live ([roadmap](../roadmap.md)).

# Sudsy

Formatter + linter for C#, JSON and YAML. `docs/ai/` holds the internal docs, which describe how everything works now (index: `docs/ai/README.md`); read the docs of the area you change first. The top-level `docs/*.md` pages are the human pages: keep them short and in sync with `docs/ai` when numbers or behaviour change. Standard brief of a build agent: `docs/ai/development/agent-brief.md`.

## Layout
- Cargo workspace in `crates/` (see docs/ai/architecture/overview.md). Language crates depend on core crates, never the reverse.
- .NET worker in `workers/csharp/` (net10.0, roll-forward). Grammars in `grammars/`, WIT in `wit/`, VS Code extension in `editors/vscode/`.

## Conventions
- HARD RULE: nothing is done in a language that can be generic. A language crate holds only facts of that language (its grammar, role and field tags, data tables, `lang.yaml` policy values, its tool's quirks as option values); every mechanism (a layout construct, spacing, rewrites, import ordering, comments, literals, a check, an analysis, a table format) lives in a shared crate and reads that data, even when only one language uses it today. A missing shared capability is built in the shared crate in the same step, never worked around in the language; "the language is older", "it has its own family", "a named gap" or "too large for this step" never justify language code (leave the gap open instead). CI enforces it: a language crate whose hand-written Rust grows needs `Language-only: lang-<name>: <the fact>` in the commit message, and the lead rejects a step whose reason is not a language fact.
- Data formats need two languages. A grammar line type, a `format.rules` section, a row key or a grammar tag read by a shared mechanism must be used by at least two languages. With one user, the mechanism stays shared Rust that takes a plain `lang.yaml` option or kind set; it becomes rows only when a second language needs it. Rows hold facts (kind sets, keywords, precedence, spacing pairs, options), not decisions (conditions, fallbacks, lookbehind): decisions stay in shared Rust. Every row is checked against its grammar at codegen, so an unknown kind, tag or key, or a row that can never match, fails the build. `cargo xtask codegen --check` enforces it in the gate and CI (every module has a `//! concept:` header, `docs/ai/kit/index.md` is generated, rows are validated, `docs/ai/design/single-use.txt` may only shrink, existing languages included: plan row V2; one exception: a concept of a shared module that reads no data, `reads:` only `option:`, `rule:` or `path:`, may stand with one user, marked `(shared)`), and `cargo xtask dupes --check` does the same for duplicated code between crates. A language step starts with the mapping table of docs/ai/architecture/adding-a-language.md and is reviewed with docs/ai/development/review-dedup.md.
- Code is cost. Every line, fixture and doc line costs agent tokens to write, to read on every later task and to update on every change. Before adding, look for what to reuse or generalize: a shared rule over grammar tags, a pattern rule (YAML) or a data row of a rule family before a Rust rule, an existing helper before a new one. Fixtures are small and focused on the rule's own cases; never copy a shared input into many folders. When a second or third copy appears, generalize it. After each new language, a generalization step follows (docs/ai/architecture/adding-a-language.md).
- Small focused modules; extract helpers instead of growing entrypoints. No duplicated logic across crates: shared behavior lives in a core crate. Code of one language embedded in another (shell in a Dockerfile `RUN`, code in a Markdown fence) is parsed with that language's own grammar and checked by its own rules, never re-read by hand in the host language.
- Errors: `thiserror` in libraries, `anyhow` only in binaries (`cli`, `lsp`).
- Snapshot tests use `insta`; fixtures live under `tests/fixtures/<lang>/` or the crate's `tests/`.
- Every formatter test checks lossless round-trip, idempotency and meaning preservation. Parity runs ratchet the count of files that change on a second format (`second-format` in `differences.yaml`): it may only go down, target 0.
- Clean up as you go: once decided, delete the losing alternatives (benchmark candidates, prototypes, bootstrap code); once X exists, move or remove what lived somewhere "until X exists". Results stay in git history.
- An upstream library (a parser such as oxc, ruff) is used for parsing only; layout and fixes are our own code on our own tree, never the library's formatter or fixer.
- The parser approach of each new language (which grammar or crate, tree-sitter or adapter) is the user's decision: the language's first step measures the candidates (speed, error recovery, language-version coverage, binary size, maintenance) and stops with a recommendation before building on one.
- Presets are pure config data. Formatter and rule code never branches on a preset or tool name (no "csharpier mode", no hidden preset-only values). Each style difference is either default behavior or a named, user-settable option documented in the schema, so any preset can be reproduced by writing its options in sudsy.yaml by hand.
- Measure performance of everything you add or change on a hot path (load, parse, format, lint, plugins, editor requests): record method, machine and numbers in `docs/ai/performance/numbers.md` (latest values only), behind a script or `perf-bench` mode so it can be re-run. Unmeasured is unfinished. Check the change against `docs/ai/performance/checklist.md` (the seven patterns behind every bench overrun) before finish.
- Breadth first: a language is done when it is usable: the formatter never changes meaning, is stable on its own output (`second-format` 0) and matches its reference tool on most real-world code (roughly 85-90%), and its lint covers the reference tool's default or recommended rule set: with the Sudsy preset that mirrors that set, on real-world code at least 85% of that set's findings are also reported by the mapped Sudsy rule on the same line (column, message and the choice among equally valid reports may differ; rules replace the tools, they do not mirror them). Then move to the next language; parity on the tool's own test suites, rare one-file causes and long-tail rules wait as named gaps or `planned` catalog entries until the language sweep is through.
- No speculative features: build what `docs/ai/roadmap.md` does not defer and the task needs (style options needed to express a preset are not speculative). When a detail is open, pick the simplest option.
- Docs describe current state, not history: update the relevant `docs/ai/` file in the same commit as the change (behavior, options, numbers, roadmap items). No milestone names or "was/used to" prose.

## Working as an agent
- Own worktree and build slot (`CARGO_TARGET_DIR`, or `.cargo/tmp/SLOT` when unset; [dev-loop.md](docs/ai/development/dev-loop.md); set up per session on the Linux agent host); write nothing outside them (not `%TEMP%`, not another slot). Don't kill processes you did not start.
- Testing while you work: `scripts/gate.sh -p <crate>` for every crate you changed (a registration change also touches `cli`), plus `cargo xtask codegen --check` after changing lang.yaml, grammars or registration. Find and fix compile, lint and test errors here, as often as you like.
- `scripts/finish.sh` is not a test run. It is the one final check of a finished step that already passes the gate: the Linux gate and the bench as parallel GitHub Actions jobs (`finish.yml`, on a pushed snapshot of the uncommitted tree), on what the change affects (a gate failure cancels the bench). It builds nothing locally; agents' runs do not queue behind each other. Run it once per step, never once per fix, and make no edits while it runs.
  - Passes: `scripts/land.sh MESSAGE-FILE` commits with the line bench appended to `bench/history.jsonl`, rebases onto origin/main and pushes (fast-forward).
  - Gate fails: `git checkout bench/history.jsonl`, fix with `gate.sh -p`, then finish once more.
  - Bench regression, even when it is the change's intended work (a new language's startup, new checks): within budget, commit and name the metrics. Standing budgets, unless the task prompt sets others: a new language's own metrics are free until its first real formatter and first default lint rules have landed (each replaces a placeholder, so there is no baseline); lint rules turned on by default, that language's lint up to +40%; format work, that language's format up to +5%; a unification step (docs/ai/design/unification.md: moving language code onto the shared crates), every metric up to +5% while the plan is open; every other metric, and every language the step does not target, up to +1%; metrics `bench.sh` marks `(informational)` (startup.providers, lint-all, alloc-instr, ...) have no budget. `bench/budgets.txt` caps always apply. Above budget, keep the bench line, stop and report the metrics and numbers; accepted, commit with that line (no second finish) and name them in the commit message; rejected, `git checkout bench/history.jsonl` and fix.
  - Check exit statuses (no piping into `tail`); never commit or push after a failure. No tags or releases.
  - Getting onto origin/main (`scripts/land.sh` does all of this): commit on your branch, `git fetch`, `git rebase origin/main`, merge the conflicting hunks (`bench/history.jsonl`: keep both sides). Never `git reset --soft origin/main` to squash after a fetch (your old tree becomes a commit that reverts everything pushed since your base), never write a whole file from a copy read before the rebase, never `checkout --ours/--theirs`: each silently reverts other agents' pushed work. Before pushing, read `git show --stat HEAD` and `git diff origin/main --stat`: every deleted or shrunk file must be one you meant to change.
- Finish (10-20 min in CI): `scripts/finish.sh --start [args]`, then `scripts/finish.sh --wait` as a foreground Bash call with `timeout: 600000`. `--wait` returns within 4 minutes, so the prompt cache (5 minutes) survives: `FINISH OK` / `FINISH FAILED: <gate|bench>`, or `FINISH RUNNING` with exit 3: call `--wait` again (or work first; no edits while it runs). No Monitor, until-loop, sleep or `run_in_background` for it. To abandon: `scripts/finish.sh --stop`.
- Other steps over 4 minutes (gate, bench, parity, corpus runs): `scripts/long.sh --start CMD`, then `scripts/long.sh --wait` (foreground) until it is not `LONG RUNNING` (exit 3). Work in between is fine. No `run_in_background`, Monitor, until-loop or sleep, and never a second launch of a running step.
- Shell commands: you already run in your worktree, so no `cd <worktree> &&`. One plain command per call: the worktree guard refuses loops, heredocs, `$(...)`, `$((...))` and variables around git, sed, wsl, pwsh or gh. Multi-step work goes in a script file (`.cargo/tmp/*.sh`), written with Write and run with `bash <file>`.
- Parity runs report real differences: never leave out or change an input to keep a run at 0; every known difference is a named `gap` (catalog or `differences.yaml`).
- Files are LF: edit with the Edit/Write tools; a script that writes files uses `open(p, 'w', newline='\n')` (Python on Windows writes CRLF otherwise, and git then warns "CRLF will be replaced by LF").
- Commit messages: a subject saying what changed, then 2-5 lines on why and what the diff does not show (behaviour change, trade-off, numbers); end with the Co-Authored-By trailer. A line `Cost-exception: shared-share: <reason>` or `Cost-exception: lang-<name>: <reason>` lets the CI `cost` check pass a fall of the shared share or a language passing its 3,000-line budget (docs/ai/architecture/adding-a-language.md). `scripts/land.sh` runs `scripts/cost.sh --languages --check origin/main HEAD` (the CI `cost` job; it is not in the gate or finish) before pushing: it fails on a language crate that grew without a `Language-only:` line.
- Steps are large: a whole piece of work in one area (a feature, or a batch of related fixes), one commit, one finish run. A task can span several steps: push after each and go on to the next yourself. A large context is no reason to stop or hand back (it is compacted automatically). Stop only for a decision the task does not cover (a regression above its budget, a denied command, a design question).
- Small work outside your step (a cleanup, a missing test, a stale branch): one line under "Small tasks" in `docs/ai/roadmap.md`, in your step's commit; don't stop to do it. Bugs go to `docs/ai/bugs.md`.
- Final report: what changed, measured results, `scripts/cost.sh` output, commits, open items.

## Commands
Run scripts in `scripts/` instead of retyping commands; reuse one before writing a new one.
On Windows run the scripts from Git Bash; `bash` in PowerShell resolves to WSL, which is not supported.
- `scripts/gate.sh [--rust-only] [--affected] [-p <crate>]...`: fmt, clippy, test, `cargo xtask codegen --check`, worker and extension checks; `--affected`: only what `cargo xtask affected` selects. Must pass before committing.
- `scripts/finish.sh [--all] [bench args] | --stop`: gate and bench in CI on what the change affects, in parallel, cancelled when a gate job fails; the check before committing a finished change. `--all`: everything (the lead, on main after a batch of merges). `-p <crate>` / `--lang <bench folder>` (repeatable) replace the gate's / bench's selection when you know it is too wide or misses something; name the override in the commit message.
- `scripts/land.sh MESSAGE-FILE`: lands a passing finish: [agent-brief.md](docs/ai/development/agent-brief.md#landing).
- `scripts/ship.sh`: push the branch, watch CI for HEAD (refuses with staged changes).
- `scripts/bench.sh [--base REV] [--all | --lang FOLDER...] [--time] | --stop`: instruction + allocation counts per phase against the merge-base (exit 1 on regression). Agents run it through `finish.sh`; by hand it needs valgrind (Windows: `scripts/bench-setup-wsl.sh` once). History: `bench/history.jsonl`.
- `cargo xtask new-rule <language> <id> [--rust]`: starter rule (pattern file, or Rust with `--rust`) + fixture; the flow is in docs/ai/development/testing.md.
- `scripts/cost.sh [<rev-range>]`: added/removed lines per category (default: merge-base with origin/main to the working tree); `--languages`: hand-written Rust per language and the shared share (`--check BASE [HEAD]`: the CI check).
- `scripts/parity.sh <tool>`: differential test of `sudsy lint` against an upstream tool on `tests/parity/<tool>/`; catalog in `docs/ai/parity/`.
- `scripts/dogfood.sh`: build debug CLI + worker into `target/dogfood/` (used by `.vscode/settings.json`, so VS Code never locks `target/debug`); restart the server after.

# The `why` of rules with one reason in every language that has them (read only when a text is asked for, see shared_why.rs).
# A section is `== id`, then paragraphs; a rule of a provider that has its own `why` keeps it.

== no-control-regex
A control character in a pattern is almost never intended: it is invisible in the source, and the
pattern then matches a character that the reader cannot see. It is usually the result of a pasted
character or of an escape that was written for something else.

To fix, remove the character, or write the one that is meant (`\t`, `\n`, `\r`) with its letter
escape.

== no-regex-spaces
Several spaces in a row are hard to count, and a pattern that has them is easily changed by an
editor that collapses white space or by a reader who counts wrongly. The number of spaces is part
of what the pattern matches.

To fix, write the number as a count (`a {3}b`).

== no-misleading-character-class
A combining mark is a separate code point that attaches to the character before it. In a character
class each code point is its own member, so the class matches the base letter or the mark alone
and never the combined character the author sees.

To fix, write the combined character as a group outside the class, or as a single precomposed
character.

== unused-variable
A variable that is never read is a leftover of changed code, or a result that was meant to be
used, so the logic that should have used it is missing.

To fix, remove the variable, or use its value.

== unused-parameter
A parameter that nothing reads is either dead weight in the signature or a sign that the body
ignores a value it should use (a typo in a name often shows this way).

To fix, remove the parameter, or use it.

== shadowed-variable
The inner name hides the outer one for the rest of its scope, so the same word means two things,
and a change that was meant for the outer variable lands on the inner one or the reverse.

To fix, rename the inner variable.

== redeclared-variable
The second declaration replaces or merges with the first, so the earlier one is dead, and which of
the two a use reaches depends on the order. It is usually a copy that should have had another
name.

To fix, remove the repeat, or rename one of them.

== redefines-builtin-id
The name hides the built-in in that scope, so a later `len(x)` or `string(b)` calls the new thing
or fails to compile far from the declaration. The code works until somebody needs the built-in in
the same scope, and then the error is hard to understand.

To fix, rename the declaration.

== doc-param-missing
The comment is what the IDE shows when the method is called and what the generated reference
lists. A parameter that is not described leaves the caller to guess what it means, its unit,
whether it may be null or empty, and what the method does with it.

To fix, add the tag that documents the parameter.

== missing-doc-comment
Documentation of the public interface is what the users of a library read, in the IDE and in the
generated reference. An element without a comment shows only its name and signature, and the
caller has to read the code to learn what it does and what it expects.

To fix, add a comment that says what the element is for.

== naming-convention
Names that follow one convention are predictable: a reader can guess the name of a thing, tell a
type from a variable at a glance and search for them. A name in another style stands out as a
mistake or as code from another project. The convention itself is a choice of the project, which
is why the expression is an option.

To fix, rename the declaration and its uses.

== unused-import
An import that nothing uses is dead code. It misleads the reader about what the file depends on,
and where an import runs the module, as in Python, it still costs the time to load it and fails
where the module is not installed.

To fix, remove the import.
